# OurTrail 多页面重构与交互设计工作流

本流程用于全站视觉改版、多页面重构、导航调整或关键任务路径重做。它不要求每个小型 UI 改动都先写完整设计文档。

## 设计边界

- 保留原生微信小程序技术栈：WXML、WXSS、CommonJS；不要为迁就网页设计技能而引入网页框架、Tailwind 或新的构建链路。
- 默认保留已有业务能力、授权边界、服务端响应和并发写入契约。页面职责、信息架构和交互可以重新设计。
- 若要改变产品规则或移除能力，先列出用户影响、服务端/数据影响、迁移与兼容性，再单独取得用户决定。
- 不把旧原型、当前 token、组件目录、AGENTS 或本技能本身视为不可质疑的终态。将其作为证据来源，核对代码和真实任务后再决定。
- 隐私、安全、平台审核、触控可达性、可读性和状态完整性属于设计约束，不因视觉改版而消失。

## 阶段一：建立现状地图

以代码和产品记录为准，核对 `miniprogram/app.json` 页面注册、各页 WXML/JS/JSON、页面级组件注册、`components/` 与 `custom-tab-bar/`。记录：

- 页面和入口的真实清单、导航关系、返回/分享/深链路径。
- 页面责任、面向的角色、依赖的数据和可执行操作。
- 共用组件、跨页状态、关键客户端工具，以及对应服务端投影/命令边界。
- 对关键写操作/权限边界，按根 AGENTS 指引查 `docs/testing/release-coverage-matrix.md` 和 `docs/testing/concurrency-consistency-model.md`，确认现有覆盖与真实契约；不要根据页面文案推断可用能力。
- loading、denied、empty、error、busy、conflict、offline 等实际可达状态；只记录真实存在或契约要求的状态。
- 当前实现与文档/原型不一致处，附文件位置或运行证据，不凭过期清单定案。

可用 `wechat-miniapp-engineering-skill` 辅助做只读页面地图与影响分析；扫描前阅读该技能的安全说明，只传入明确的项目路径，不把 AppID、密钥、用户资料或原始敏感值复制进报告。其扫描结果是索引，仍须回到源码核实。

## 阶段二：从用户任务推导结构

识别真实角色和高频/高后果任务，按任务整理入口、前置条件、主要操作、成功反馈、失败恢复、退出/返回路径。把跨页步骤和责任边界画成简明流程或 Mermaid 图。

随后制定页面职责与导航方案：

- 每页回答一个清楚的用户问题，避免仅因组件存在就保留独立页面。
- 说明入口、主操作、次操作、页面间跳转、上下文传递和返回后的状态。
- 对活动创建、报名、组织者处理、同行安排、现场执行、天气/行程查看等流程，检查从发现到完成的闭环及异常回路。
- 对新增/合并/拆分/迁移页面逐项说明依据、影响和兼容策略。

## 阶段三：交互与状态规格

先描述行为，再决定视觉。对每条关键任务写清：

- 触发方式、输入、校验、确认、忙碌态、成功结果和下一步。
- 取消、重复点击、弱网/离线、无权限、数据为空、服务端拒绝、版本冲突时的反馈与恢复。
- 表单草稿/自动保存、危险动作确认、导航返回与页面重入行为。
- 辅助信息、提示语和按钮标签怎样让用户理解“现在的状态”和“可以做什么”。

只为实际存在的业务情况增加状态；不得假造服务端能力或把权限判断移到客户端。每个状态都要对应明确文案、视觉表达和可行动作（若有）。

## 阶段四：视觉方向与组件系统

提出少量可比较的视觉方向，并以品牌、户外场景、信息密度、单手操作、长文本和数据优先级来评估。方向确定后，再整理：

- 色彩语义、层级、字号、间距、圆角、阴影/边界、图标与插图规则。
- 组件职责与变体、交互状态、禁用/忙碌/聚焦状态，以及何时不应使用。
- 页面模板和内容密度规则；为天气图表、地图、名单/车辆等领域控件保留合适的表达方式。
- token 和组件迁移表：旧值/旧组件、目标、消费者、验证方法、暂时保留项。

视觉概念不得压过可读性、状态解释或动作优先级。颜色不能是状态的唯一编码；检查正文对比度、字号、触控目标、动态文字换行和窄屏布局。

## 阶段五：形成可审阅方案

在批量改页面之前，提供足以做决定的设计包：

1. 现状页面/角色/任务地图和已核实的问题。
2. 目标信息架构、导航树、页面职责与关键流程图。
3. 关键页面的结构草图或线框，以及核心交互/状态规格。
4. 视觉方向、组件原则、token 变更提案和原生小程序实现映射。
5. 分阶段页面清单、依赖关系、风险、每阶段验收条件和回退点。

标明已知事实、设计建议、尚待用户裁决的决定。设计方案通过用户审阅后，再按阶段实现；一次聚焦一个业务流程或一组紧密关联页面。

## 阶段六：原生实现与验证

- 将设计结构映射到原生页面/组件，不新增框架或依赖；复用业务工具与服务端契约。
- 先验证公共 token/组件，再迁移页面；避免新旧样式无期限并存。
- 每阶段检查页面四态、交互后果、权限和错误恢复，并运行静态门禁。
- 改 WXML/WXSS/组件结构后，按 `docs/e2e-mp/README.md` 与 `docs/e2e-mp/automation-playbook.md` 做开发者工具渲染/交互验证；截图或元素数据应覆盖主要状态和关键视口，静态门禁不代表像素正确。
- 使用 `tools/e2e-result.js` 及 `docs/testing/e2e-result-semantics.md` 的语义报告结果；业务通过不能代替 UI 通过，通道退化不得记作通过。
- 对照本技能的交付清单审查，同时记录未验证项；不得把推测写成真机已验证。

## 完成标准

- 每个注册页面都有明确角色、任务和入口/出口归属；无人负责的重复页面或死入口已裁定。
- 核心任务可从入口走到完成，并说明主要失败/恢复路径。
- 视觉与交互规则可在原生 WXML/WXSS/CommonJS 中落实，且组件和 token 有单一、清楚的归属。
- 服务端授权、业务状态、持久化和并发语义未被前端改写。
- 受影响页面有真实渲染与交互证据；尚未覆盖的设备、视口或状态明确列为未验证。
