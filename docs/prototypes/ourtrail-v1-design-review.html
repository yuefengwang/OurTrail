REVIEW 01 · SEP 2026
01 / THE PRODUCT BET

让一次户外活动，
从发起到出发，都变得简单。

先成为领队下次还想用的组织工具，再成为户外资源网络。活动是所有人共同的协作现场，不是一件待售的旅游商品。

OUTSIDE, TOGETHER.

把反复确认的事，
变成清楚的下一步。

参与者知道在哪里集合，领队知道谁还没到，司机知道本车接谁。出发之后，仍有人跟进每个人的安全状态。

01

活动先于发现

先看到我的下一场、待办与最近打开的私域分享，不用假活动广场制造繁荣。

02

身份跟着任务走

同一个账号，可以参加一场、组织一场，也可以只负责一辆车。

03

结束不只是点一下

行程结束后继续确认安全到家，未关闭异常不能从工作台消失。

先验证“好用”，不虚构收入模型

原规划的效率目标，不是已达成指标
≤ 10 min从模板发布一场常规活动
≤ 2 min完成一位参与者报名
再用一次领队下一场主动复用，而非回到群接龙

02 / SCOPE, NOT A FEATURE PARADE

V1 做深一次活动，
不提前做大一个平台。

本次以完整 V1（V1.0–V1.2）作为原型边界；四个任务视角共享同一场活动，不是四套独立系统，也不是俱乐部 SaaS 后台。

BUILD / 现在做深

报名到安全收尾

活动创建与分享、本人/同行人报名、人员名单、候补、集合签到、车辆分配、节点、异常、天气、通知、安全到家。

围绕单次活动私域传播
REFRAME / 换一个入口

任务，不是频道

首页 → 我的活动中心
消息 → 活动通知
司机 → 本车任务
实时位置 → 最后上报位置
俱乐部工具 → 组织者工作台

保持后续版本边界

不放灰色占位入口：活动广场、找搭子、司机抢单、领队认证、俱乐部主页、路线社区、聊天和支付，均不进入 V1 导航。

03 / ONE ACTIVITY, SHARED CONTEXT

三个底栏入口，
一个活动中心。

首页回答“我的下一步是什么”，详情回答“这场活动怎么参加”，工作台回答“这场活动还缺什么”。参与者不被管理工具包围，领队不用反复找功能。

三种组织方式，推荐任务驱动的活动中心

A · 推荐

活动中心 + 场景工作台

活动通知我的

最短履约路径；未来发现可单独扩展。代价：冷启动首页不呈现陌生内容，需要认真设计空状态。

符合私域定位与已确认角色ADR
B · 不推荐

五频道消费型导航

发现活动搭子消息我的

利于成熟期探索，但 V1 没有内容供给与匹配能力；易变成空广场和重复列表。

公开发现与搭子越过版本边界
C · 不推荐

多角色独立门户

参与者端领队端司机端

各角色操作清晰，但入口重复，身份切换割裂；不符合一账号多场活动的使用方式。

与场景直达和页面复用决策相悖

“活动”是一切关系的入口

实线为 V1 · 虚线为未来挂接

角色切换改变界面，不改变授权

PARTICIPANT

参与者

默认进入。看本人和代报同行人；知道下一步，不能浏览全员个人资料。

ORGANIZER

活动组织者

创建后进入本场工作台。组织别的活动不代表能管理当前活动。

STAFF

协作 / 收队

授权任务链接直达。分管名单、节点、异常；没有车辆配置和全量导出。

VEHICLE CONTACT

车辆联系人

本车任务直达。车上接谁、去哪接、谁上车；不看到医疗或紧急联系人。

04 / FROM INVITATION TO HOME

四种任务视角，
跑通同一条履约链。

不是给每种功能一个页面，而是在当前阶段把最需要完成的事放在手边。报名在活动前，签到在集合时，安全确认在行程结束后。

参与者从分享直达活动
群分享→详情 / 风险→报名→等待确认→看集合与车辆→签到→途中报备→安全到家
组织者无前置认证申请
空白 / 模板→预览发布→微信分享→确认人员→分车 / 分座→集合通知→签到出发→节点 / 异常→安全收尾
协作 / 收队只对分管队员负责
任务链接→确认负责范围→协助签到→记录后队节点→上报 / 跟进异常→协助确认到家
车辆联系人不是司机接单平台
车辆链接→上车点 / 路线→逐人确认上车→车辆出发→返程清点→结束本车任务

三个独立状态维度，避免一个枚举承载所有事情

设计提案 · 不照搬旧 Demo 的日期判断
ACTIVITY / 活动执行
草稿→已发布→集合中→活动中→行程结束 · 待到家→已归档
REGISTRATION / 招募条件（派生，不覆盖活动阶段）
开放名额已满 → 仍可候补截止 → 停止新增报名取消 → 清理所有未履约安排
SIGNUP / 每个实际参与者的资格
未报名→待确认 · 占位→已确认→个人签到 / 上车 / 到家记录

满员时进入候补，不占位；取消或未通过会释放名额。候补由领队手动转为待确认，不偷偷改变家庭同行人的状态。

轻量审核，不增加第二次“加入”

提案：一个组织者完成确认；“已报名”是结果说明，“待确认/已确认”才是资格状态。待确认占用名额，不能分车；确认后才进入已加入。无审核活动直接确认。

需要确认的规则 R1

安全到家是完成条件，不是装饰按钮

“结束行程”不强制伪报安全；进入收尾页，保留未到家和未解决异常。所有实际出行者有到家确认、未出发者已核实且异常关闭，才可归档。

需要确认的规则 R3
名额、同行人、改点、取消和现场例外的具体规则
场景拟采用规则必须保持的约束
多人报名每位实际参与者独立Signup，共享报名组；余位不足时整组候补并解释原因，用户可返回调整人数不静默拆开同行组；提交者不等于参与者
重复提交 / 多人抢最后名额幂等请求；提交时重新检查名额，失败返回余位或候补选择并保留表单待确认 + 已确认 ≤ capacity
候补转正组织者选人进入待确认；占位和状态写入一起完成不超位，不直接自动加入车辆
取消一个同行人默认仅取消选中人员；明确确认后才取消整组同一变更释放占位、车辆和座位；其他人不受影响
修改上车点未分车直接改；已分车且未集合时撤下旧分配进入待重新安排并通知；集合后走领队协调不保留与上车点不一致的旧车辆安排
签到≠上车自助签到记录到集合点；车辆联系人确认实际上车，两个状态独立无定位可人工核实签到；签到不自动标已上车
出发前有人未到阻止不经确认的出发；先逐人记录迟到安排、核实未出发或线下协调结果不要求100%签到才永远无法出发，也不自动忽略失联者
途中退出 / 下撤保留履约及异常记录，不能用取消报名删除；记录接应与确认结果下撤者仍需安全确认；未到者必须核实未出发
多人活动跨天用完整带时区startAt/endAt；时间只提示阶段，不自动替代组织者结束与归档第二天不能因开始日期已过去而变成已结束
取消活动仅草稿/发布/集合阶段取消；活动进行中以终止行程进入收尾，不擦除履约已取消不再签到；原名单只读且保留必要审计
所有例外都回到活动详情或工作台，不产生孤立结果页。下一章 · 页面布局 →

06 / OURTRAIL DESIGN SYSTEM

像户外装备一样，
克制、可靠，随时能用。

深林绿建立可信感，石灰白保证阅读，少量嫩叶色标记即将出发的状态。户外气质来自材质、留白和真实路线信息，不靠山峰、太阳和帐篷堆砌。

事务边界、失败语义和性能成本
操作同一提交内必须完成失败行为
报名 / 候补转正资格记录 + 名额检查 + 关联事件无部分占位；表单保留；解释满员或已截止

签到 / 节点 / 到家目标人员状态 + 操作人 + 时间 + 人工说明重试幂等；不因点击按钮就在其他视角假成功

原型承诺单标签页内多角色共享一致状态；不承诺真实分布式并发。生产需云函数事务、幂等键、资源鉴权和审计，不能复制localStorage当后端。敏感数据只用合成样本；未知的生产保留期不在这里随意指定。

自动分车只在用户请求时执行：保留既有安排，按上车点分组，优先整组同行，无法容纳时留下明确未分配项；不做全局路径优化。对本场n人/m辆车的简单分配约O(n·m)，渲染派生最多扫描本场名单，不扫全平台活动。这里是成本推导，尚无性能实测。

09 / REVIEW, THEN BUILD

最值得先改的，
不是颜色，而是产品定义。

版本路线方向合理，但有四处缺少实施口径。以下明确分开“已定边界”和“本次补充建议”，不要求你重复批准已有 ADR。

需要确认的设计补充

R1

轻量确认，必须把占位说清楚

推荐：默认单负责人审核，待确认占位、确认后可分车；可选无需审核时直接确认。没有两层审批，没有再次“加入”。代价：待审核会占位，工作台必须显著提醒处理。

R2

分座是车辆安排，不是座位销售

推荐：分车为必需，座号为可选；领队分配/交换，参与者只看自己的；小车不必强制编号。可用乘客位=核载−司机−不可用位，司机不能被重复计入。

R3

行程结束与安全归档分开

推荐：结束后进入待到家；不阻止行程结束，但未核实人员与未结异常阻止归档。不能把未到直接算安全，也不能用活动取消清掉途中异常。

R4

权限冲突采用最新、最小范围

推荐：司机不看紧急联系人；历史敏感资料受限；位置进入收尾停止上报并提供撤回。具体生产留存期限在上线前由合规确认，不编造“永久保存”或随意删历史。
