# 彩虹遮光闸修复 —— 满天云为什么能拿"条件较好 ★★★★"

日期：2026-10-10 · 基线：`origin/master` = `abf08f0`（三层架构切片一+二集成后）
分支：`win/weather-v2-rainbow-gate` · 触发：用户真机截图三连问「这个天气真有可能出现彩虹、星空、银河吗？」

## 1. 截图里三张卡分别是什么性质

| 卡 | 星级 | 分数构成（`sky.js`） | 判定 |
|---|---|---|---|
| 星空 ★★ | 36 = 晴空率 0% 的 8 分 + 新月月照 1% 的 28 分 | **否定式陈述**，文案自己写「观星条件差（暗夜晴空 0%）」 ⇒ 星级与文案一致 | 正常 |
| 银河 ★★★ | 48 = 银心季底分 20 + 晴空率 0% 的 **0 分** + 新月 28 分 | 第三颗星**几乎全是"月黑"给的**，天空一分没得；文案写「不建议抱太大期望」 | 星级与文案有张力，但**不是 bug**：月黑确实是必要条件之一。登记为呈现层可议项，本轮不动 |
| 彩虹 ★★★★ | ≥70 | 起步 40 + 「湿小时 ≥2」30 = 70，**全程没看过云能不能让太阳照出来** | **判据缺陷，本轮修复** |

## 2. 根因（一句话：把遮光物当成了水分信号）

`sky.js` 的彩虹逐时标记原来是：

```js
const wet = c.precip > 0.05 || c.showers > 0.05 || (c.rh != null && c.rh >= 88) || c.low >= 70
if (solar.altitude < 40 && solar.altitude > -2 && wet) add(h, 'rainbow')
```

`c.low >= 70`（低云 ≥70%）被当成"空气有水分"。但低云恰恰是**把太阳遮住的东西**，而彩虹的必要条件是"太阳在身后照得出来 + 反日方向有水幕"。于是：

- 全天 100% 云、一滴雨没下 ⇒ 每小时的 `low>=70` 都成立 ⇒ 满分的"水分"信号 ⇒ 4 星；
- 同一天、同一份云量数据，**光染（alpenglow）判 0 分**并明说「云量或降水条件不足」——两个现象对同一个物理事实的态度互相矛盾，这就是"哪里不对"的答案。

真实快照上的放大效应（改前，`ab-rainbow.json`）：峨眉山 7 天里 **6 天彩虹 = 100 分**，成都 50–70 分——彩虹卡几乎天天"条件较好"，与"能不能看到"无关。

## 3. 复现（合成数据喂真实 `sky.summarize`）

|---|---|---|

| 低云 10% 但中高云铺满 | `rainbow 90 条件较好` | `rainbow 0 条件较差` |
| 干燥晴 | `rainbow 0` | `rainbow 0` |

## 4. 修法（复用文件里已有的两个口径，不新造数字）

```js
const wet = c.precip > 0.05 || c.showers > 0.05 || (c.rh != null && c.rh >= 88)   // 去掉 c.low >= 70
const sunVisible = c.low < 40 && (c.mid + c.high) / 2 < 30                        // 新增遮光闸
if (solar.altitude < 40 && solar.altitude > -2 && wet && sunVisible) add(h, 'rainbow')
```

- `c.low < 40` ← 光染分支已有的「低云少（光能到山体）」同一个数、同一句语义；
- `(c.mid + c.high) / 2 < 30` ← 星空/银河「暗夜晴空」分支已有的同一个数；
- 两个数都**不是新阈值**，是把文件里既存的两条口径用到它们该用的地方。
- 顺带：`rainbowConclusion` 的否定文案改成说清"还得真能看到太阳"；`item.look` 的方位角改为取整（真机出现过「约 284.15999999999997 度」，`anti` 是 `norm360(solar.azimuth+180)` 的原始浮点；银河那句只是碰巧 `galaxyBearing` 内部已取整）。

**已知局限（写清楚，不假装解决）**：模型只有整点云量，没有方向分辨能力，无法表达"我这边下雨、太阳从云缝里照出来在另一侧"这种局地条件。所以这道闸会把某些真能出彩虹的时刻一起挡掉（漏报换误报）。文案仍用概率语言，不说"会有"。

## 5. 影响面证明（`tools/ab-rainbow.js`，PRE = `origin/master`）

这是一次**故意的**业务变化，所以判据不是"零差异"，而是两条更强的：

```
合计 33 个场景：彩虹判定变化 19 处、非彩虹越界 0 处
✓ 改动被限制在彩虹这一类，且确实起作用了
```

- **非彩虹越界 = 0**：其余五类结论（云海/光染/星空/银河/晨昏光窗口）的分数与档位、以及除 RAINBOW 之外的全部机会窗口（type/起止/置信）逐字相同；
- **彩虹变化 > 0**：若为 0 就说明这道闸在生产数据上从没生效，等于白改 —— 脚本对两种情况都 exit 1。
- 场景 = 5 个合成极端 + 真实快照 4 站 × 7 天（`real-cloud-g2.json`）。明细存 `ab-rainbow.json`。

## 6. 判据有没有牙齿（`tools/mutate-rainbow.js`）

先过有效性门「未变异副本 3 套全绿」，再注入 5 条退化：**5 条 0 漏网**。

| 变异 | 结果 |
|---|---|
| R1 水分信号退化成"只看低云" | ✓ sky-test + oi-claim-gate 红 |
| R2 整个遮光闸拆掉 | ✓ 同上（`有降水但满天云 ⇒ 必须消失` 那条红） |
| R3 遮光闸只看低云（不管中高云） | ✓ sky-test 红 |
| R4 中高云阈值放宽到 300（永不生效） | ✓ sky-test 红 |
| R5 方位角回到未取整浮点 | ✓ sky-test 红 |

**R3 是这套脚本存在的理由**：第一版测试只写了"低云满"的用例，把闸改成"只看低云"时三套全绿——也就是"中高云遮日"那一半根本没被测到，补了断言才会红。
**另一次收获是反向的**：原本 R1 写成"把 `|| c.low >= 70` 加回水分信号"，结果三套全绿。查下来这不是漏网而是**等价变异体**——`low >= 70` 与遮光闸的 `low < 40` 互斥，加回去也是死分支。教训记进 AGENTS 铁律 32：**判"漏网"之前要先确认变异体在行为上真的不等价**，否则会把"改不动结果"误读成"测试有牙齿"。
