## 0. 一句话结论

现有输入足够支持「天文时刻」和「单点云况事实」，但**不足以支持银河 / 星空 / 彩虹 / 云海 / 晨昏光染当前给出的星级和「概率较大」式断言**。问题不是阈值调得准不准：其中四项的必要条件包含「某个方向上的云 / 降水 / 地形 / 天空亮度」，而现有数据是**单点垂直柱**，没有这些维度。黄金 / 蓝调 / 日出日落是唯一的例外——它们只依赖太阳几何，输入是充分的。

| 天相 | 输入是否足够 | 主要缺口 |
|---|---|---|
| 黄金 / 蓝调 / 日出日落 / 天文暗夜始（时刻） | ✅ 足够 | 无（天气只影响可见性，不影响时刻） |
| 星空 | ❌ 不足 | 低云、月亮高度、光污染、大气透明度、地平线 |
| 银河 | ❌ 不足 | 银心高度/方位、月亮高度与角距、光污染、方向云、跨夜窗口 |
| 彩虹 | ❌ 不足 | 降水方向/雷达、反日点地平线；现只有单点降水 |
| 云海 | ◐ 部分 | 单柱云带 + 点海拔有了；缺逆温、温湿廓线、山谷地形、水平云分布 |
| 晨昏光染 / 日照金山 | ❌ 不足 | 目标山峰、坡向、DEM、视线；轨迹走向不是目标方位 |
| 天文暗夜始的「银河与深空窗口」 | ❌ 继承银河缺口 | 机会句依赖 `galaxy` 标记 |

先承认系统已经做对的部分：它把天文时刻、云量、降水和海拔出处分开，页首也明确写了「概率判断，不是出发许可；云层与云海为模型推算」（`miniprogram/pages/weather/weather.wxml:12`），OI 还显式声明了「光污染与地形遮挡无数据源」（`miniprogram/utils/outdoor-intelligence.js:50-52`）。**问题在于这些边界没有传导到主结论卡的星级和「概率较大」上**：用户读的是卡片，不是页首免责声明。

## 1. 先把「人物所在经纬度」说清楚

天气页当前的判定主体是**查询点**，不是人物本人：

- 坐标来源是路线节点、`wx.chooseLocation` 地图选点、或手填经纬度（`miniprogram/pages/weather-hub/weather-hub.js:76-93`、`:107-139`）。
- 天气模块没有消费实时定位；`activity.js:691-695` 的 `wx.getLocation` 用于签到/位置上报，不进入天气页。
- `format.js:181-184` 写「本项目没有任何 wx.getLocation 路径」，这句话已经**过时**（仓里有 3 处 `wx.getLocation`），但它对天气页的结论仍成立：天气页不知道用户本人站在哪里。
- 页面在海拔与云层位置处使用「此点」主语（`format.js:186`、`:223-224`），这是准确的；银河的「朝西南 231 度找银心带」和彩虹的「朝 X 度看」则隐含「你就在此点」。

所以：
- 如果用户问的是「我计划到达的那个点，今晚怎么样」——当前点语义是对的，应该继续保持「此点」。
- 如果用户问的是「我现在站的地方怎么样」——需要把 `wx.getLocation` 接进天气查询，这是新的产品/隐私决策，不是算法微调。
- 在当前实现下，用户离开路线节点后，页面显示的仍是计划点，不是他脚下的点。

## 2. 系统实际拥有的输入

来源主要在 `cloudfunctions/trailApi/lib/weather.js` 与 `miniprogram/utils/astro.js`、`sky.js`。

| 输入 | 现状 | 证据 | 备注 |

## 3. 逐现象：必要输入 vs 当前支持

### 3.1 银河

**必要条件**（缺一不可）：
1. 天文暗夜：太阳高度 < -18°。
2. 银心在地平线以上（最好 > 10–20°），且有明确高度/方位。
3. 云：视线方向上的低/中/高云少；银河带方向尤其重要。
4. 月光：月相 + **月亮高度/方位** + 与银心的角距；月亮在地平线下时照亮百分比不应计入。
5. 光污染 / 天空亮度：城市近郊和荒野是两回事。
6. 大气透明度 / 气辉 / 水汽。
7. 地形：银心方向的低空是否被山脊挡住。
8. 时间窗口：今晚日落后到明晨天文晨光始，跨零点。

**当前支持**：

| 必要输入 | 当前 | 证据 |
|---|---|---|
| 天文暗夜 | ✅ | `sky.nightHours`（`sky.js:131-140`） |
| 银心高度/方位 | ❌ | `galaxyBearing(date, hour)` 只有月份 + 经验方位表；**签名没有 lat/lng**（`astro.js:221-241`） |
| 银心季 | ◐ | 只按月份 3–10（`astro.js:212-216`），不按纬度和时刻 |
| 云 | ◐ | 只看中/高云均值（`sky.js:378`）；低云完全不参与 |
| 月光 | ◐ | 只有照亮百分比（`astro.js:203-210`），没有高度/角距 |
| 光污染 | ❌ | 无 |
| 透明度/地形 | ❌ | 无 |
| 跨夜窗口 | ❌ | `detail` 只含所选自然日（`weather.js:582`），见 §4.2 |

**结论：输入不足。** 当前「银河可见概率较大」和「朝 X 度找银心带」至少缺银心高度、月亮高度、光污染和方向云四项。

合成复现（30°N, 103°E, 2026-07-15）：`galaxyBearing('2026-07-15', 22)` 返回 `128`，函数本身不接收经纬度；同一钟点在 45°N、87°E 会得到同一个数。中国的统一北京时间在西部与当地太阳时最多差约 2 小时，而这张表是以「北京时间的钟点」为横轴的（`astro.js:218-223`），所以西部地区的「往哪看」会系统性偏早/偏晚。

### 3.2 星空

**必要条件**：
1. 天文暗夜。
2. 低/中/高云都少；低云在观察点之上会挡住天空，在脚下则不一定。
3. 无降水/雾/霾。
4. 月光：月相 + 月亮高度。
5. 光污染。
6. 大气透明度 / seeing。
7. 地平线/地形。

**当前支持**：

| 必要输入 | 当前 | 证据 |
|---|---|---|
| 天文暗夜 | ✅ | `sky.js:131-140` |
| 云 | ◐ | 只算 `(mid + high) / 2 < 30`（`sky.js:344`）；低云不看 |
| 降水 | ◐ | `precip === 0`；缺失值会被 `hourCloud` 变成 0（`sky.js:116-129`） |
| 月光 | ◐ | 只有照亮百分比；`starConclusion` 与 `astro.starSight` 两套阈值不一致 |
| 光污染 | ❌ | 无 |
| 透明度 / seeing | ❌ | `visibility`/`rh` 可用但未进入星空判定 |
| 地平线 | ❌ | 无 |

**结论：输入不足。** 合成输入「低云 100%、中高云 0、无降水、新月」得到星空 **73 分 / 条件较好 / ★★★★ / possible**，因为低云完全不参与判定。若这个点在 500 m 的山脚，低云就在头顶，星空实际不可见；当前算法分不出来。

还有一个更硬的复现：当 `cloud` 三键缺失（`cloud: {}`）时，`sky.starConclusion` 给出 **73 分**，但同一张卡的文案来自 `astro.starSight`，写的是「夜间云量高，观星条件差（暗夜晴空 100%）」——**分数与文字互相打脸**。原因是两套实现：`starConclusion` 用 `hourCloud` 把缺失变 0，`starSight` 直接做 `undefined + undefined = NaN`（`astro.js:250`）。如果 `cloud` 整个对象缺失，`starSight` 直接抛 `TypeError: Cannot read properties of undefined (reading 'high')`。

### 3.3 彩虹

**必要条件**：
1. 太阳高度 0–42° 且太阳本身可见（不被云/地形挡住）。
2. **反日方向**正在下雨/有雨幕；单点降水不等于反日方向有雨。
3. 反日点在地平线以上，观察者背后视野开阔。
4. 雨幕与阳光同时存在（破碎云、阵雨）。
5. 无地形遮挡。

**当前支持**：

| 必要输入 | 当前 | 证据 |
|---|---|---|
| 太阳高度 | ✅ | `solarPosition`（`astro.js:160-177`）；但代码允许 `> -2°`，太阳已落到地平线下也可能被算 |
| 太阳可见 | ◐ | 用低云 <40、中高云均值 <30 代理（`sky.js:218`） |
| 水分 | ◐ | 单点 `precip/showers/rh`（`sky.js:217`） |
| 降水方向 | ❌ | 无雷达/无风向降水 |
| 反日点地平线/地形 | ❌ | 无 |
| 彩虹弧高 | ✅ | `42 - solar.altitude`（`sky.js:419`） |

**结论：输入不足。** 可以支持「太阳高度合适 + 单点有降水/高湿」，不能支持「彩虹可能出现」的星级，更不能把「朝 X 度看」当成出现方向——那只是反日点的几何方向，不是雨幕所在方向。

### 3.4 云海

**必要条件**：
1. 观察点高于低层云/雾的云顶，且两者之间净空足够。
2. 低层有足够的云量/厚度（层云、积云、雾），而不是任意高度的云带。
3. 逆温/稳定层 + 低层湿度，把云压在谷地。
4. 山谷/盆地地形，让云「成海」；平地上的一条云带不是云海。
5. 高空云少（能看到云顶）。
6. 风弱，且不会把云吹散。
7. 时间（清晨/傍晚）与可见性。

**当前支持**：

| 必要输入 | 当前 | 证据 |
|---|---|---|
| 云带低于观察点 | ✅ | `band.base/top` + `elevation`（`sky.js:293-309`） |
| 云带高度 | ◐ | `cloudBandAt` 把所有 ≥80% 层合并成一条 band，**不分低/中/高**（`weather.js:106-123`） |
| 低层云类型/逆温 | ❌ | 只有云量和位势高度，没有气压层温度/湿度 |
| 山谷地形/水平云分布 | ❌ | 单点垂直柱，无 DEM、无 3D 云场 |
| 高空云少 | ✅ | `high < 30`（`sky.js:311`） |
| 风 | ◐ | 10 m 风速 <15 km/h（`sky.js:313-314`） |
| 可见性 | ❌ | `visibility` 可用但未进入云海判定 |

**结论：部分支持。** 它能确认「此点在一条 ≥80% 云带的上方」，不能确认「云海」。合成输入「3500–3800 m 云带、观察点 4000 m、清晨高层云 0、风 5 km/h」得到 **云海 74 分 / possible**，文案写「云带偏高（底约 3500 m）」却仍然给「云海机会」——这正是把中高层云带当成云海。并且窗口是「清晨 00:00–08:00」，00:00–05:00 是黑夜，主结论卡没有做民用晨昏裁剪（OI 的 `visibleSeaWindow` 做了，主卡没做，见 `agenda.js:97-104` 与 `weather.js:1128-1150` 的差异）。

另外，若该日没有 `band`（例如气压层数据缺失），`cloudSeaConclusion` 直接输出「今天没有成层的低云带…云海无从形成」并判 `excluded`（`sky.js:293-297`）——**把「没取到」印成「没有」**，违反仓库自己的铁律 26②/34⑤。

### 3.5 晨昏光染 / 日照金山

**必要条件**：
1. 太阳在晨昏窗口内。
2. 目标山体存在、在视线内、坡面朝向太阳。
3. 观察点到山体之间低云/霾/降水少，光能到山体。
4. 中高云可以作为「天空被染色」的增强项，但它不是「山体被光染」的必要条件。
5. 地形/地平线遮挡。

**当前支持**：

| 必要输入 | 当前 | 证据 |
|---|---|---|
| 晨昏窗口 | ✅ | `astro.photoWindows`（`astro.js:139-153`） |
| 低云/中高云/降水 | ✅ | `sky.js:198-206`、`:254-262` |
| 目标山峰/坡向 | ❌ | `sky.js:275` 自陈没有 |
| DEM/视线 | ❌ | 无 |
| 轨迹走向 | ◐ | `heading` 是路线前后节点连线（`weather.js:1199`），不是目标山峰方位 |

**结论：输入不足。** 合成输入「3500–3800 m 中高云带、低云 0、观察点 4000 m」得到 **光染 92 分 / possible**，文案是「晨光在 06:00-06:00 有山体被光染的可能…」，紧接着又说「本工具没有目标山峰的位置、坡向、遮挡（DEM）数据，给不出某座山会不会金山」。前半句已经越过了后半句承认的边界。

### 3.6 黄金 / 蓝调 / 日出日落 / 天文暗夜始

**必要条件**：只有太阳高度角穿越点 + 日期 + 经纬度 + 海拔。当前全部满足（`astro.js:105-153`），而且页面把它们当客观时刻、不做概率判断（`sky.js:439-460`）。这部分不需要改算法；唯一要注意的是「天文暗夜始」后面的「银河与深空窗口」是机会主张，已由 `hasMark(galaxy)` 控制（`agenda.js:167-169`），但它继承银河的缺口。

## 4. 跨现象的系统性问题（比单个阈值更优先）

### 4.1 缺测被当成 0，方向还不一致

`sky.hourCloud`（`sky.js:116-129`）用 `num(x) || 0` 把 `null/undefined` 变成 0：

- 云量缺失 → 0% → 星空/银河的晴空率变 100%（**有利**）。
- 降水缺失 → 0 → 星空/银河判「无降水」（**有利**）。
- 低云缺失 → 0 → 光染的「低云少」加分（**有利**）。
- 但 `astro.starSight` 直接读 `h.cloud.high`，缺失时是 `NaN/TypeError`（**不利/崩溃**）。

同一份缺测数据，在不同函数里可以变成「条件好」或「条件差」，这比阈值偏差更危险。**先做输入可用性门**：缺关键字段时返回 `unknown`（仍出卡、说明缺什么），不要返回 `possible` 或 `excluded`。

### 4.2 夜段只算所选自然日，缺掉后半宿

`weather.js:582` 的 `detail` 只筛 `h.d === this.data.date`；`sky.nightHours` 只能在这个 24 小时里取「凌晨到天文晨光」+「天文暮光到 24:00」（`sky.js:131-140`）。以 2026-07-15、30°N、103°E 为例，卡片窗口是 `00:00-04:00 / 22:00-23:00`，**07-16 的 00:00–04:43 没有进入判定**；而 `series` 里其实有这一天，图表 `buildChartMarks` 也按天全量算（`weather.js:1212-1223`）。结果是：同一个「今晚」的图表与结论卡看的不是同一段夜。

文案「夜段延续到次日，晨段属前夜尾段」（`sky.js:354`）承认了混用，但没有解决「今晚后半夜」缺失。对银河/星空，后半夜往往是最佳窗口之一。

### 4.3 银河方位表不是星历，且忽略经纬度/时区

`galaxyBearing(date, hour)` 只吃日期和北京时间钟点，不吃 lat/lng（`astro.js:221-241`）。表本身是按北纬 25–40° 的经验曲线，且以北京时间为横轴。中国西部（约 87°E）与东部（约 120°E）的当地太阳时差约 2 小时，同一钟点的银心高度/方位并不相同。当前算法无法表达这个差异。

### 4.4 月亮只有相位，没有高度

`moonInfo` 只算月龄/照亮百分比（`astro.js:203-210`）。月光是否影响观测，取决于月亮是否在地平线上、高度多少、离目标多远。当前「月照 30%」在月亮已落下和月亮高挂时被当成同一件事；星空/银河的月照评分因此既可能高估也可能低估。

### 4.5 低云不参与星空/银河，云带不区分层次

- 星空/银河只看 `mid/high`（`sky.js:344`、`:378`），低云完全不看。
- 云海的 `band` 是「所有 ≥80% 气压层的合并」（`weather.js:106-123`），没有低/中/高标签；3500 m 的中层云带也能被写成「低层有云带」。

正确做法不是简单把低云加进去，而是**按云层高度与观察点海拔判断**：低云在脚下不挡天顶，在头顶就挡。现有 `cloudLevels` 有 22 层高度，足以做这件事，但 `sky.js` 没有消费它。

### 4.6 云量/降水是单点柱，不是三维场

Open-Meteo 返回的是查询点垂直柱：逐时低/中/高云量、气压层云量/位势高度、地面降水。它没有：

- 水平方向的云分布（南边地平线有没有云）；
- 降水的空间分布/移动方向（反日方向有没有雨幕）；
- 山谷地形（云海到底在哪个谷）；
- 目标山峰的位置/坡向（哪座山被照亮）。

银河（银心方向的低空云）、彩虹（反日方向降水）、云海（谷地云海）、光染（目标山体）都依赖这些维度。**这不是调阈值能补的，是数据维度缺失。**

### 4.7 总评会放大单项

`conditions.overallGrade` 只把 `score >= 45` 的项放进均值（`conditions.js:88-99`）。如果只有银河一项「有戏」且分数虚高，总评就会变成银河的分数。单项输入不足会直接传导到「徒步条件 ★★★★」。

### 4.8 同一现象有两套实现

`astro.starSight`（`astro.js:247-277`）与 `sky.starConclusion`（`sky.js:331-359`）都算晴空率和月照，阈值不同、缺测处理不同；`starConclusion` 的文案用前者、分数用后者。合成输入 `cloud:{}` 已经复现「73 分 + 夜间云量高」的矛盾。优化算法前应先收成一套。

## 6. 建议的优化顺序

### Phase 0：先把已有输入用对（客户端，无新数据）

1. **输入可用性门**：`sky.summarize` 对每个现象先检查关键字段；缺测返回 `unknown` 并说明缺什么，禁止 `null → 0` 的有利默认。
2. **收掉第二套实现**：`astro.starSight` 与 `sky.starConclusion` 合成一套，统一晴空率/月照/缺测处理。
3. **跨夜窗口**：用 `series` 拼出「所选日入夜 → 次日天文晨光」；图表与结论卡同一窗口。
4. **月亮高度**：纯天文计算，先解决「满月在地平线下也被扣分」「月牙高挂却不扣分」。
5. **低云按高度参与**：用 `cloudLevels` + 点海拔判断低云在头顶还是脚下。
6. **银心高度/方位**：至少加经度时差；能上真星历就上真星历（这会推翻 `astro.js:218-223` 的「不是星历」决定，需要产品裁决 + 改测试）。
7. **文案与评级同步降级**：银河/星空加「未计入光污染/透明度」；彩虹改「条件」而不是「概率」；云海改「云带之上」；光染拆「天空」与「山体」。

### Phase 1：补同源数据（云函数 + 重部署）

- Open-Meteo 增加气压层温度与相对湿度（如 925/850/700 hPa），用于：
  - 逆温/稳定层判断（云海）；
  - 低层湿度廓线；
  - 更细的云海/光染条件。
- 这是同一 provider、同一 key，成本主要是请求字段和返回体大小；改 `cloudfunctions/trailApi/lib/weather.js` 后必须重部署并同步 `trailApiLab`。

### Phase 2：外部数据/产品决策

- 光污染（Bortle/SQM 静态图或用户输入）；
- DEM/地形 horizon/谷地；
- 雷达/nowcast（彩虹）；
- seeing/透明度（天文天气）；
- 实时用户位置（如果产品要「我所在位置」而不是「此点」）。

## 8. 证据边界

- 本报告所有「当前支持/不支持」均为 E1（源码可直接核对）或 E2（合成输入复现）。
- 合成输入只用于证明**算法在边界输入下的行为**，不代表真实预报。
- 未跑真机：页面像素、真实预报下的星级分布、各地实际可见性均未验证；若要升 E3/VERIFIED，需按 `docs/e2e-mp/README.md` 的三道门槛做真机截图，并用真实快照跑分布。
- 本报告没有修改任何生产代码；`cloudfunctions/` 零改动，因此不涉及重新部署。
