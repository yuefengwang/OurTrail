## 1. 为什么 Meteoblue 看起来专业（对截图 2 的逐层拆解，回答 §2 七问）

**1) 为什么"专业、可信"？** 因为它**只陈述、不劝导**。整张图没有一个形容词、没有一个结论、
没有一次"建议你"。可信度来自三件事：连续性（每小时的值都在，没有跳变和留白）、可对齐性
（三行面板共享同一条时间轴，雨柱和风羽能逐列对照）、可核对性（坐标、海拔、单位、图例、
模型信息全部印在图上）。用户觉得"它没想说服我"——这正是 OurTrail 现页最缺的气质
（现页 6 张结论卡在"劝导"）。

**2) 怎么把不同变量放到同一条时间轴上？** 三个手段：
- **共用 x 轴**：温度/降水/风三个面板同宽同刻度，任意时刻竖着读一列就是"那个小时的完整天气"；
- **变量换行不换轴**：温度是线、降水是柱、云是灰阶剖面、风是箭头+曲线——**形态服务变量语义**，
  但全部锚在同一条 24h/日 的轴上；
- **上下文层垫底**：昼夜底色（黄=昼）、日分隔线、"now"虚线铺在所有面板之后，时间感不需要文字解释。

**3) 为什么云层高度表达特别重要？** 因为对户外而言"有云"没有信息量，**"云在几米"才是决策变量**：
垭口 4200m 的人关心的是灰阶到底压在 2km 还是 5km。截图 2 右侧的 Altitude (km) 轴 + 灰阶云量剖面
让"我会不会在云里"变成一次视线对照，而不是一次心算。**这是 meteoblue 对徒步者最大的单一价值，
也是 OurTrail 云海能力的可视化基础**（我们的气压层云带 + 观景点海拔线是它的强化版：多了一条
"你在这里"的横线）。

**4) 为什么连续曲线/柱/图标比文字结论可信？** 文字结论是**说话者的判断**，曲线是**可复核的数据**。
连续表达同时传递了数值和**变化率**（"午后云量在涨"不需要文字，斜率就是）；柱状图的位置就是时间、
高度就是量级，没有四舍五入的说辞空间。**图形是自我证明的，文字是要被信任的。**

**5) 用户如何借此自行判断"今天适不适合徒步"？** 专业徒步者的实际读法（也是本设计要服务的路径）：
先看降水柱找空窗 → 看灰阶剖面确认云在哪个高度 → 对照风羽看窗口稳不稳 → 用昼夜底色对齐自己的行程
（"06–18 是白昼，我的窗口在第一段"）。**产品不替他下结论，只把结论需要的全部证据排好队。**

**6) OurTrail 应该学什么？** ①一条时间轴承载全部事实（我们 V2 的 24h Weather Timeline）；
②云按高度表达（云层带剖面行 + 观景点海拔线，比 meteoblue 更进一步回答"云在我脚下还是头上"）；
③形态服务语义（温度线/降水柱/风向羽）；④上下文层垫底（昼夜/now/日分隔）；
⑤把"结论"彻底请出事实区（Meteoblue 图上没有任何我们的判断）。

**7) 不应该照搬什么？** ①配色与品牌（绿底红线的 meteoblue 视觉是它的资产，OurTrail 有自己的
forest/leaf 纸面语言）；②桌面信息密度（1560px 塞进 375px 实测不可读，见原型实测）；③英文界面
（Image API `lang` 无中文，未来接了也只能是外文图——这本身就是要用自绘解决的一点）；④卡通 picto
（OurTrail 用文字承载语义的既有语言）；⑤多模型概率话术（我们没有多模型时不伪装）。

> **一句话结论（任务 §2 的目标句）：** 专业天气产品负责提供 Evidence，OurTrail 负责解释 Evidence。
> Meteoblue 的图是 Evidence 的形态学范本；OurTrail 的差异化是"解释 + 决策"，不是把 Evidence 复述一遍。

## 2. 三种视觉集成方案（§7/§8/§9）

> 授权前提（详见 meteoblue-integration-v2.md）：修改/裁剪/overlay 未获公开许可 → **按禁止处理**；
> `lang` 无中文；16,000 credits/图；375px 整图缩放实测不可读。

### Option A：完整 Meteoblue Meteogram（整图即内容）

```
地点 → [Meteoblue Meteogram 原生宽横滚] → OurTrail Analysis
```
- 优点：专业感最强、开发最省（一张图）、用户熟悉。
- 缺点：品牌属于 meteoblue；英文界面；375px 实测不可读 → 只能横滚 4+ 屏；自定义零；
  credits 最贵；修改/裁剪未获许可。
- **判定：不推荐。** 只在"用户主动点开查看大图"的次级入口里有意义。

### Option B：Meteoblue 作为「专业天气预览」槽位（重点候选）

```
格聂 · 3500m
7-Day（降权重）
────────────────────
专业天气 · Meteoblue     ← 信任锚（原生宽横滚 or 折叠）
────────────────────
为什么值得关注            ← OurTrail 分析的入口桥
☁ 云海    ★★★★☆ 较好     ← 结论层
🌌 银河    ★★★☆☆
────────────────────
24h Weather Timeline      ← 决策工具（自绘，云层带剖面）
Today's Outdoor Agenda
Evidence / Why?
Detailed Numbers（折叠）
```
- 理念：**Meteoblue 负责建立"天气数据可信度"，OurTrail 负责把天气变成户外决策。**
- 事实（原型已实现，`prototype/meteoblue/`）：模拟图 + 可读性对照 + OurTrail 分析层全部成立。
- 启用前提（缺一不可）：付费 license + 商务书面确认缓存/展示/attribution + credits 预算。
- **判定：视觉结构采纳为 V2 页面的「Meteoblue 槽位」设计，数据源暂用自绘图顶替（见 decision.md）。**
  即：**槽位是真的，图先是我们自己的**——未来接不接 meteoblue 不改变页面结构。

### Option C：Meteoblue 图 + OurTrail Overlay

- 前提问题："Meteoblue 是否允许修改/裁剪/overlay？"——**公开文档无此许可，`no_logo` 是付费项，
  按保守原则判定为不允许。**
- **判定：禁止，不做任何实现。** 且技术上也无必要：我们的自绘 24h 时间轴原生就是"事实 + OurTrail
  标记"的同图分层（云海窗口底色、黄金时刻带），效果等价、语言是中文、无任何授权约束。

## 3. 移动端 Meteogram UX（§23 的正面回答）

**实测证据**（`prototype/meteoblue/`，截图 `screens/04–05`）：1560px 桌面图缩到 375px = 22%，
图例文字 ≈3.1px——**不可读**，这不是"横向滚动"能解决的（缩放把字缩小，滚动不改变密度）。

**因此 V2 的移动端答案不是"缩小"，而是"重绘"：**

1. **24h 一屏**：OurTrail 自绘时间轴按 24h × 12.5px/时布满 375px，免滚动；
2. **点击取详情**：点任一小时列 → 浮条（该小时全部数字 + 天相归属），不靠在图里挤文字；
3. **48h/72h 用横滚但保持原生字号**（12.5px/列不变，加宽画布而不是缩小像素）；
4. 7 天宏观趋势交给降权重的 7-Day 条 + （未来）Meteoblue 槽位横滚，**不与 24h 决策图争夺首屏**。

这就是 fallback 原型已经实现、Option B 原型结论框里写明的那句话：
**"桌面图不能整图缩放塞进手机——只能原生宽横滚，或按 24h 重绘。" OurTrail 选重绘。**
