## 2. F1 光污染语义单源（失败关闭）

### 2.1 现状与根因

- `sky.js:787`（star）与 `sky.js:907`（galaxy）：`lpMissing = ctx.lightPollution === null`——
  只有**显式 null** 触发"封顶 69 + 未计入披露"。
- `weather.js:678-680`（skyCtx）与 `:773-775`（factsFor ctx）：增强输入未就绪时传 `undefined`。
  三个真实状态产出 `undefined`：①首屏渲染（`loadSkyContext` 未回）②`getSkyContext` 整体失败
  （`.catch`，`_skyContext` 保持 null）③配额用尽/非 ready（`weather.js:550-560`）。
- 探针复现：星空 null=69 vs undefined=73；银河 null=69 vs **undefined=88**。
- `conditions.factsFor:251` 的证据行同样只认 `=== null`，undefined 时连"光污染未计入"行都不出。
- **已有门禁钉住现行契约**：`sky-test.js:698`「没有 lightPollution 字段 ⇒ 保持旧行为（不封顶）」。

### 2.2 方案

1. `sky.js` 三处 + `conditions.js` 一处，`=== null` 一律改为 `== null`（undefined 与 null 同等失败关闭）。
   理由：纯函数无法区分"调用方没有这个概念"与"问了没取到"；按铁律 26②，未知不能读成有利。
2. `weather.js` 不动亦可（F1 的核心在 sky 侧），但把 `loadSkyContext` 失败路径的
   `skyInputNote` 与卡片披露对齐（已有文案，仅确认不再需要新措辞）。
3. **契约替换而非削弱**：`sky-test.js:698` 改为
   「字段缺失（undefined）与显式 null 同样封顶 69 且披露」——把"保持旧行为"这条**换成更强的判据**，
   并在测试注释里写明替换理由（页面三个真实状态都产 undefined）。

### 2.3 验收

- `sky-test` §21：新增 `noFieldStar`/`noFieldGal` 断言 `score === 69 && /未计入光污染/`；
  旧断言（`score > 69`）删除并注释替换原因。
- 变异自证：把 `== null` 改回 `=== null` ⇒ 新断言必须红（否则门是假的）。
- A/B（`ab-lp-semantics.js`）：28 天真实快照，唯一允许差异 = star/galaxy 的 score 封顶与披露文案；
  越界定义含"LP 有读数时逐字节相同"（阳性对照，证明不是无条件封顶）。
- 真机：E3 可选（分数变化不新增文案，披露文案已有）；若跑，验配额用尽路径的卡片。

### 2.4 风险

首屏在增强输入到达前显示封顶后的分数，到达后可能升星——方向是单调向好，可接受；
需在 `skyInputNote` 已有措辞内说清"部分输入未计入"。

## 3. F2 光污染差时的星级封顶 + 去重

### 3.1 现状

`sky.js:925` 只为月光设了封顶（注释原话："文案已经说'不建议抱太大期望'，星级必须与之一致"），
光污染分支没有。探针：Bortle 8 + 晴空 + 新月 ⇒ 银河 **78 ★★★★☆「条件较好」**，
文案"光污染较高…不建议抱太大期望"。星空同样可达 74（45+28+大气 11−10）。
附带缺陷：galaxy 文案里"光污染较高"出现两次（`reason` 链 + `lpText`）。

### 3.2 方案

1. 抽一个共用小助手（单源，放 `sky.js`）：
   `function cap69(score, cond) { return cond && score > 69 ? 69 : score }`，
   把 `sky.js:925` 的月光封顶改写为它，四处矛盾分支统一调用：
   - galaxy：`cap69(score, moonEffective >= 35 || lpPoor)`
   - star：`cap69(score, lpPoor)`（星空月光分支最高 62，不需要）
   - cloudSea（F3）：`cap69(score, 云带偏高)`
2. 去重：`lpText` 在 `reason` 已点名"光污染较高"时不再重复该短语，只保留来源署名
   （署名同时存在于 `factsFor` 的"天空亮度"证据行，不丢信息）。

### 3.3 验收

- `sky-test`：Bortle 8 + 晴空 + 无月 ⇒ star/galaxy 均 `≤69` 且文案含"不建议/条件一般"；
  Bortle 2 不受影响（阳性对照）。
- 变异：删掉 `lpPoor` 条件 ⇒ 红；`cap69` 改成 `>= 69` 之类的边界扰动 ⇒ 红。
- A/B：允许差异仅限 lpPoor 场景的 star/galaxy score 与披露文案。

## 4. F3 云海：民用晨昏裁剪 + 云带分层

### 4.1 现状

- 探针 P2：云带只在 01–05 时 ⇒ 主卡 window `"01:00-05:00"`、文案"清晨 01:00-05:00 有…机会"（88 分）。
  凌晨是黑的。`agenda.visibleSeaWindow` 与 OI 都裁，**主卡不裁**。
- 探针 P1：3500–3800 m 中高云带 + 观察点 4000 m ⇒ 74 ★★★★☆，
  理由写"云带偏高（底约 3500 m）"却仍说"有在云顶之上看云海的机会"。
  根因：`band` 是所有 ≥80% 气压层的合并，无低/中/高标签（`weather.js` `cloudBandAt`），
  `baseMin≤2200` 只值 14 分差价。
- `agenda.js:11-13` 注释声称"可见性规则是 presentation 层唯一一处裁剪"——修主卡会打破这句话，
  需把裁剪收成单源（见下）。

### 4.2 方案

1. **裁剪单源**：`sky.js` 新增纯函数 `civilClip(hours, sun)`（民用晨光–暮光交集，缺天文数据不裁剪），
   `cloudSeaConclusion` 的 `list`/`window`/`windowText` 改用它；`agenda.visibleSeaWindow`
   改为委托同一判据（保持签名与现有行为，`outdoor-cloud-sea-test` 32 条零改动通过），
   并把"唯一一处裁剪"注释改写为指向 `sky.civilClip`。
   注意依赖方向：`agenda → sky` 已存在，`sky → agenda` 会成环，故判据只能住 `sky.js`。
2. **云带分层**：`baseMin > 2200` 时——
   - 文案去掉"低层"断言，改"云带偏高（底约 X m，可能不是贴地云海）"；
   - 走 `cap69` 封顶（文案已说"机会低"，星级必须一致）；
   - `verdict` 保持 `possible`（"此点在实心云带上方"是几何事实，判过了成立；
     把中高云带一律 excluded 是过度修剪——站在中云云顶上看云海是真实体验）。
3. 标记行（`hourMarks` 的 `cloudSea`）**不裁剪**：图表是事实层，黑夜里的"云带在此点下方"
   仍是事实；可行动窗口只在卡/日程裁。此为既有分层立场，本次不改。

### 4.3 验收

- `sky-test`：新增 ①黑夜云带 ⇒ 窗口被裁到民用晨昏且文案不再写"清晨 01:00"；
   ②3500 m 云带 ⇒ `≤69` 且无"低层"断言；③低云带清晨 ⇒ 分数与改前逐字节相同（阳性对照）。
- `outdoor-cloud-sea-test`：委托重构后 32/0 零改动（行为相同证明）。
- A/B（`ab-cloud-sea.js`）：28 天真实快照，允许差异仅限 cloudSea 的 window/score/文案；
   越界定义含"非 cloudSea 卡一动即红"。
- 真机：VERIFIED 要求（窗口与星级是用户可见变化，按三道门槛截图）。

### 4.4 风险

中高云带日子的云海卡从 4 星降 3 星——这是**故意的业务变化**，验收不用零差异，用上面的越界定义。

## 5. F4 跨夜窗口统一（分两阶段）

### 5.1 现状

结论卡的 `night` 是跨夜序列（`nightHoursForDate`），但日程/OI/证据锚点都按当日 24h：
- 探针 P6：银河卡 possible + "06:00 前后（次日）"，当日日程**无**银河窗口、
  "天文暗夜始"的机会句 sub 被摘 null。
- 探针 P7：卡窗口"次日 06:00"，证据行锚点全在 20:00（`factsFor` 取当日 dusk 小时），
  "看图↗"跳到银河没升起的小时。
- 第一版探针还复现：日程 05:00–06:00"银河窗口"实为**前夜尾段**，与卡上"次日 06:00"同屏并存。

### 5.2 阶段一：锚点与 bestAt（低风险，先做）

1. `sky.summarize` 的各结论项**新增附加字段** `at`（best/first 小时的 `dateTHH:mm`），
   不改任何既有字段（附加字段结构不变）。
2. `conditions.factsFor` 的 galaxy/star 分支：`ctx.night` 存在时优先用结论项的 `at` 做锚点，
   回落才用 dusk 小时。页面 `buildCondCards` 调用处把对应 item 传进 ctx。
3. 验收：P7 复现用例转绿（锚点落在次日 06:00 或该小时的最近可见列）；
   `factsFor` 既有输出在非跨夜场景逐字节相同（阳性对照）。

### 5.3 阶段二：日程与 OI 的今晚窗口（需一次呈现层裁决）

1. **日程**（垂直列表，安全）：`buildDayAgenda` 接受可选 `nightHours`（跨夜小时序列，
   带 `d` 标记）。夜间天相（galaxy/star）按今晚序列聚类，次日小时的事件标 `次日 HH:mm`
   并排在当日事件之后；排序改day-aware。`astroDusk` 的机会句 sub 改问"今晚序列"是否有 galaxy 标记。
2. **OI 24h 卡**（时间轴是单日 0–1440，不能造假跨度）：
   - 列表项用跨零点表示（`oi-presentation` 已有 `isCrossMidnight`/`timeLabel`，
     如"今晚 22:00 → 次日 04:00"）；
   - **时间轴跨度只画 24:00 前的段**，次日段不画（画在今日最左端是谎）；
     在列表项文案里说明后半夜部分。这是保守默认方案。
   - **备选方案（需产品裁决）**：把 24h OI 卡整体改成"今晚–明晨"语义——
      taps/spans/刻度全动，爆炸半径大，本文不默认采纳。
3. `sky.hourMarks` 对次日小时的判定已正确（`h.d || date`），`buildChartMarks` 逐日算也已覆盖，
   本阶段不动图表。
4. 验收：P6 复现——日程出现"银河窗口 今晚 xx → 次日 06:00"、`astroDusk` sub 恢复；
   OI 列表项标签正确、时间轴无越日假跨度；A/B 允许差异仅限夜间天相的日程/OI 条目；
   48/72h horizon 卡行为逐字节相同（阳性对照）。

### 5.4 风险

阶段二是七项里爆炸半径最大的（agenda/OI/呈现三处）。若阶段一上线后真机样本显示
跨夜银河窗口占比很低（可先用 28 天快照统计），可把阶段二降级为"只在结论卡注明"。

## 6. F5 总评与单项的关系

### 6.1 现状

`conditions.overallGrade:105-107`：`live = score>=45` 的项取均值，无一达标则全取。

### 6.2 方案

单项独高的日子总评降一档，需在 A/B 里给出分布（预计影响真实快照中 X/28 天，跑完填数）。

### 6.3 验收

- A/B（`ab-overall.js`）：28 天快照总评差异全部可归因到"单项独高"规则，无其他差异。

## 7. F6 光染拆分（文案为主）

### 7.1 现状

探针 P3：低云 0 + 中高云 60 + 无降水 + 朝东 ⇒ 92 ★★★★☆，
"晨光在 06:00-06:00 有山体被光染的可能"，同句自认没有目标山峰/坡向/DEM 数据。
即"天空与云霞被染色"（真有戏）被按"山体被染"（无数据）出星级。

### 7.2 方案

1. **无地形数据时**（`terrainAt` 为 null）：文案改口为"晨昏窗口天空与中高云有被染色的条件（…）；
   没有目标山峰数据，判断不了哪座山会被染（日照金山）"；`look` 改"朝东至东北看天空与山脊线"；
   **分数不动**（它回答的是"这个窗口的光线条件多有戏"，天空染色是真实可见现象）。
2. **有地形数据时**：维持现有"山脊线"口径（DEM 山脊是真实输入）。
3. 顺带统一标记与加分的两把尺：`mid+high≥25` 才出标记、`≥40` 才加分 ⇒ 25–40 区间
   会出现"4 星但理由里没有'可被染色'"。方案：加分改两档（≥40 +14 原文案；
   25–40 +8"中高云偏少"），**不新造数**（两个界都是现成的）。
4. `factsFor('alpenglow')` 已列低云/中高云/降水，无需改。

### 7.3 验收

- `sky-test`：无地形 ⇒ 文案不含"山体被光染"且分数与改前相同；有地形 ⇒ 逐字节相同（阳性对照）；
  25–40 区间 ⇒ +8 档存在且理由同步。
- 真机：VERIFIED（文案是用户可见变化）。
