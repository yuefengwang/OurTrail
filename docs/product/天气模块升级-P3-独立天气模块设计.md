## 1. 背景与问题

当前天气的唯一入口链路是 **活动 → 路线节点 → 天气**：`pages/weather` 必须携带 `activityId`，
云函数 `getWeather` 必须先加载全量状态找到活动与节点坐标才能查询。这条链路在"我已经建了活动"
的场景下工作得很好，但把天气锁死在了活动语义里：

1. **查天气的前提居然是先建活动。** 徒步者最常见的实际场景恰恰发生在活动存在之前——
   "看到一条路线攻略，先看看那座山周末有没有云海""这条轨迹值不值得开一队"。此刻没有活动、
   没有节点，天气功能完全不可达。
2. **查询条件被迫绕道。** 想查"四姑娘山大峰 4500 米这周六"的天气，需要建活动、导 GPX、
   保存草稿、进详情、点节点——为一个只读查询走完整个创建流程，成本倒挂。
3. **天气本身是高频独立需求。** P1/P2 已经把单点查询的展示能力做到位（7 日概览、meteogram、
   天相、云层带），这套能力被埋在活动三级链路下，与它的价值不匹配。

## 2. 目标与非目标

**目标**

1. 新增独立天气模块（天气 Tab），脱离活动即可使用，无需档案、无需登录态校验（沿用 getWeather 免鉴权语义）。
2. 三种输入形式：
   - **导入 GPX 轨迹** → 自动提取标注点（名称/经纬度/海拔）→ 按点查询；
   - **地图选点**（wx.chooseLocation，自带地名搜索）→ 查询；
   - **手动输入经纬度**（含可选名称/海拔）→ 查询。
3. 查询到的点可保存为本地「观察点」，导入的轨迹存为「轨迹点组」，下次免重传。
4. 查询结果页与活动天气页同构：7 日概览条、meteogram、天相结论、云层带、全图横屏全部复用。
5. 查询可分享：接收方点开即看，无需任何前置（活动无关、档案无关）。
6. 活动流（详情 → 节点 → 天气）现状行为完全不变。

**非目标**

- 观察点不做云端同步（V1 全本地，wx storage；跨设备同步列后续）。
- 不做地名文本搜索的地理编码 API 接入（地图选点自带搜索框已覆盖；Open-Meteo geocoding
  对中文山名/地名覆盖质量存疑，评估后再议）。
- 不做自动「最近查询历史」（保存动作是显式的；自动记录列后续预埋）。
- 不做逐分钟降水、雷达图、天气订阅消息推送。
- 不做多点多日对比表。
- 不改动活动流天气页的既有行为与契约。

## 3. 关键决策（概览）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 天气以**第 4 个 Tab** 进入（活动/天气/通知/我的） | 用户定位"有意义且常用"；发现页式的浅入口配不上查询频次 |
| D2 | **两页分工**：新 Tab 页 `weather-hub`（模块首页）+ 现有 `pages/weather`（查询视图，泛化） | 平台约束是承重墙：`wx.navigateTo` **不能打开 Tab 页**，而活动流（activity.js 详情→天气，activity.js:335/364）与分享链路都靠 navigateTo 带参直进查询视图，查询视图永远不能进 tabBar；Tab 页又只能 `switchTab` 进入（不能带参），hub 必须自包含。两条合起来，两页分工是平台强制而非风格选择——未来任何"合并两页"的简化提议都应被此条拒绝 |
| D3 | 查询视图改造为**点来源无关**：`src=activity`（现状）与 `src=local`（自由查询）两种模式 | 展示装配逻辑（7 日条/meteogram/天相/云层带）100% 复用，不为自由查询复制一个页面 |

| D5 | 云函数**新增 action `getWeatherByPoint`**，不改 `getWeather` 契约 | 显式路由是本项目惯例；活动路径零风险；底层 `fetchForecast`/缓存完全共享 |
| D6 | 手动输入提供「GPS 原始坐标（WGS-84）」开关，客户端转换后入库 | 俯仰之间：天气模型分辨率公里级，500 米偏移不影响结果，但**存储口径必须唯一**，否则将来上图必错 |
| D7 | 分享仅开放 local 模式 | 活动天气页依赖 participant 视角读取，非参与者可能被拒；自由查询无此依赖 |

## 5. 查询视图泛化（pages/weather 改造）

### 5.1 模式定义

| | `src=activity`（默认，现状） | `src=local` 单点 | `src=local` 轨迹组 |
|---|---|---|---|
| 入参 | `id`(activityId), `point?`, `date?` | `lat, lng, name?, ele?, eleSrc?, date?` | `set`(轨迹组id), `point?`, `date?` |
| 点来源 | `api.read` 活动视图 → `routeSnapshot.points` | 入参直接构造单点 | `watch-points.listTracks()` 按 id 取点集 |
| 节点抵达日程 | `RS.schedule(points, startAt)`，startAt=活动出发时刻 | 无 schedule 概念 | `RS.schedule(points, 基准日+GPX锚点钟点)`，见 §5.4 |
| 路线关键点 picker | 显示（多节点，含第几天标签） | 不显示；静态点卡（名称+坐标+海拔来源） | 显示（与活动流同款，含第几天标签） |
| 云函数调用 | `api.getWeather(activityId, pointId, date)` | `api.getWeatherByPoint({lat, lng, date})` | 同左（按当前节点坐标） |
| 生成天气提醒草稿 | `isOwner` 时显示（现状） | 永不显示 | 永不显示 |
| 「保存此点」 | 不显示（预埋：活动节点一键收藏） | 显示，写入本地观察点 | 不显示（节点已在组里，防重复散点） |
| 分享 | 不开放（预埋） | `onShareAppMessage`，单点全套 inline 参数 | 分享**当前节点**（按单点形式内联；12 点塞 URL 不合理） |
| heading（日照金山方向） | 前后节点连线求走向 | null（无走向可依，天相卡降级） | 前后节点连线求走向（与活动流一致） |

### 5.2 实现要点

- `reload()` 拆为 `resolveContext()`：按模式装配 `{points, schedule, initialDate, isOwner}`，
  装配后走**同一条** setData（date 与 pointIndex 同轮落定的竞态纪律不变，见 SYNC 2026-09-28
  日期竞态条目）→ `fetchWeather()`。
- 模式判定宽容化：`src` 省略时按入参推断——有 `set` 或 `lat/lng` 即 local（手输 path、
  分享参数被截时更皮实）；local 单点与轨迹组在 resolveContext 内部分流，后续装配同轨。
- 轨迹组 id 在本地存储里找不到（组已删除后点旧入口/旧会话返回）→ status-panel denied
  （"轨迹组已删除"），零外呼。
- **新增 `getPoints()` 取点方法（原文误写为「改为」，实为新写）**：`weather.js` 现状**没有**
  `getPoints`，而是把 `this.view.activity.routeSnapshot.points` 内联读了 5 处——
  `fetchWeather:168`、`headingAt:259`、`onDraftNotice:454` **无守卫**，
  `pickInitialPoint:149`（经局部变量）、`nodeElevation:369` 有守卫。local 模式没有 `this.view`，
  前三处会直接抛 TypeError。因此 `getPoints()` 必须是**模式感知**的统一取点入口（按 §5.1 表格
  分流 activity / local 单点 / 轨迹组），一次性替换全部 5 处内联读，而不是可选清理。
  云函数调用按 `this.mode` 分支；`covers()` 缓存判定的 `pointId`：单点用常量 `'local'`、
  轨迹组用组 id，窗口内切日复用照常生效。
- local 模式 `wx.setNavigationBarTitle` 显示查询点名（weather.json 的「天气参考」只留给活动流）。
- local 模式入参校验：lat/lng 必须为有限数（lat ∈ [-90,90]、lng ∈ [-180,180]），非法时
  `status-panel` denied（"坐标不完整，无法查询"），不发请求。
- `name` 缺省时的点名称：`'北纬 31.06 · 东经 121.38'` 式坐标文案，不显示"未命名"。
- 海拔来源标签照旧：入参 `ele` 有效 → 「手动填写」或「GPX 记录」（由 hub 传 `eleSource`，
  缺省「模型降尺度（±300-600 m）」）。

### 5.3 分享（local 模式）

- `title`：`{名称} {日期} 天气 · {当日天气短语}`（如「四姑娘山 2026-10-03 天气 · 多云」）。
- `path`（单点/轨迹组当前节点统一按单点内联）：
  `/pages/weather/weather?src=local&lat=..&lng=..&name=..(encodeURIComponent)&ele=..&eleSrc=gpx|manual&date=..`
  ——参数体量极小，走 URL 合理（对比：168 小时序列走 chart-store 内存交接，两条纪律并存不矛盾）。
  `eleSrc` 一并传递（评审补）：否则接收方看到海拔数字却没有来源标签，或被误标为模型降尺度。
- 接收方**无需档案、无需活动关系**：查询视图 local 模式不调 `api.read`，
  云函数 `getWeatherByPoint` 免 OPENID（见 §8）。接收方也可「保存此点」到自己设备。
- **⚠️ 评审补：分享 URL 会携带精确坐标（lat/lng 到小数点后 5～6 位）+ 名称 + 海拔，
  原文未讨论其隐私含义。** 这是本仓**新引入的先例**：现有唯一分享链路
  `pages/activity/activity.js:189` 只带不透明 `activityId`，从不带坐标。
  风险具体化：分享者若选了自己家附近的点，群内任何人点开即知其精确住位。
  同一份文档在别处对敏感信息相当克制（紧急联络/健康备注是「按用途读取、用后即弃」）。
  **建议二选一并写入 §14 待确认**：(a) 分享前弹一次确认，文案点明「对方会看到你选的精确坐标」；
  (b) 分享链接只带 `lat/lng` 并按 §6 的 3dp 网格**降精度**（≈百米，足够定位山头），
  不带 `name`/`ele`。本仓取态是「宁可少给信息也不泄露」，倾向 (b)。

### 5.4 轨迹组的抵达日程（评审补：现成能力，别扔掉）

初版设计让 local 模式 schedule 全 unknown，与 §9.4「节点行显示第几天」自相矛盾。而
`utils/route-schedule.js` 本身就支持：`schedule(points, startAt)` 传 startAt 得
「第 N 天 HH:mm」+ arriveDate，不传得「出发后 X 小时」。轨迹组查询应传：

**startAt = 基准日 + GPX 锚点（首个有时间戳节点）的钟点**

- 钟点取自 GPX 记录本身——抵达钟点自然就是出发钟点，无额外偏移（P2 已确立原则）；
- **基准日 = 首次进入页面时的日期（入口 date 或今天），会话内不随切日重算**。必须避开的
  循环陷阱：若基准日跟着"当前所选日期"走，切到某节点会把日期带到它的抵达日，抵达日又成为
  新基准日、整个行程再平移一天，日期会一路向前漂。基准日定死在入口，切日只是查看（与活动流
  "用户手选日期"行为一致），想换基准日就从 hub 带新 date 重新进入；
- 日期优先级链复用：用户手选 > 节点推算抵达日（基于基准日展开）> 入口日期 > 今天；
- 无时间戳轨迹自动落「无时间信息」，单点没有 schedule 概念——均无需特判。

## 6. 观察点（本地数据模型）

新增 `miniprogram/utils/watch-points.js`（仿 draft.js：纯 wx storage，无云依赖）。

```js
// 单点
WatchPoint {
  id: 'wp-<36进制时间戳><随机>',       // 生成后不变，供删除/去重
  name: string,                       // 可为空，展示时回退坐标文案
  lat: number, lng: number,           // 一律 GCJ-02
  ele: number|null,                   // 米；null = 用模型海拔
  eleSource: 'picked'|'manual'|'gpx', // 决定查询视图的海拔来源标签
  createdAt: ISO 字符串,
}
// 轨迹点组（一次 GPX 导入）
TrackSet {
  id: 'wt-...',
  name: string,                       // 文件名去 .gpx
  importedAt: ISO 字符串,
  stats: { count, distanceKm, ascentM, hasEle, hasTime },   // 见下方校对说明
  points: TrackPoint[],               // ≤12，即 parseGpx 的 points 输出
}
// 轨迹组节点 = WatchPoint 超集：多一个 time（GPX 时间戳，ISO instant|null），
// 供 RS.schedule 推算「第几天/几点到」——parseGpx 已输出，透传即可，
// 别像当年丢 ele 那样在某一层静默抹掉
TrackPoint { ...WatchPoint 字段, time: ISO|null }
```

**评审校对（`stats` 字段与 parseGpx 实际返回对不上，落地前须按实际取值）**：
`parseGpx` 返回的顶层是 `distanceKm` / `ascentM`（`gpx.js:306-307`，**恒为数字、不可能为 null**，
原文的 `|null` 有误导），其 `stats` 实为
`{ waypoints, routePoints, trackPoints, hasElevation }`（`gpx.js:309-314`）——
**既没有 `hasEle` 也没有 `hasTime`**。因此 hub 组装时：
`distanceKm/ascentM` 从顶层取；`hasEle` 可由 `stats.hasElevation` 映射；
**`hasTime` 无法从 `stats` 取，须遍历 `points` 自行判定**（每点 `time` 是否为有限值）。
本仓既有教训：字段在某层静默丢失去难（editor 丢 `ele`），这里显式写明来源以免实现时再丢一次。

- 存储 key：`ourtrail.watchpoints.v1`（单点数组）、`ourtrail.watchtracks.v1`（组数组）。
  **沿用 `draft.js` 的既有约定**——点号小写命名空间 + `.v1` 版本后缀
  （`ourtrail.drafts.v1` / `ourtrail.opened.v1` / `ourtrail.openid`）。
  原文写的 `ot_weather_points` / `ot_weather_tracks` 不可用：`ot_` 前缀在本仓是
  **云端集合**的命名空间（`store.js` 的 `ot_profiles` 等），拿来当本地 storage key 会与云端语义混淆。
- 容量：单点 ≤ 20，组 ≤ 10；超限时保存动作给出明确提示（"最多存 20 个点，先删一个"），不静默挤掉。
- API：`listPoints / savePoint / deletePoint / listTracks / saveTrack / deleteTrack`，
  读写即时落 storage；返回值均为拷贝（防调用方误改缓存）。
- 手动输入若勾选 WGS-84：入库前用 `utils/gpx.js` 的 `wgsToGcj` 转换，**库存永远只有 GCJ**。
  hub 查询视图传的是 GCJ 值，云函数 `gcjToWgs` 纠偏链路与活动路径完全一致。
- 去重（评审补）：保存时与既有单点比对坐标（3dp 网格 ≈ 百米级），命中即提示
  「已有很近的观察点：{name}，替换吗？」——替换沿用原 id 与 createdAt，仅更新名称/坐标/海拔，
  不产生重复行。

## 7. 三种输入形式（hub 页）

### 7.1 地图选点（主路径）

- `wx.chooseLocation`（`requiredPrivateInfos` 已声明 chooseLocation；隐私指引已含「位置信息」）。
- 返回 `{name, address, latitude, longitude}`（GCJ-02）→ 组装 WatchPoint：
  name 取 `name || address || ''`，ele 为 null（查询时用模型海拔，展示如实标注）。
- 平台差异提示：开发者工具内该 API 行为受限（可能返回默认位置），验收以真机为准。

### 7.2 手动输入经纬度（兜底）

- dialog 弹层表单：名称（可选）/ 纬度 / 经度 / 海拔（可选，米）/「这是 GPS 原始坐标（WGS-84）」勾选框。
- 客户端校验数值合法后再允许提交；WGS 勾选时转换后入库。
- 选项说明文案一句：「从奥维/两步路等导出的坐标多为 WGS-84；微信地图里的坐标不用勾」。
  诚实说明：对天气结果本身，约 500 米的系统偏移远小于模型分辨率（公里级），这个开关
  主要是保证**存储口径唯一**——这些点将来参与地图展示时不会偏移。

### 7.3 导入 GPX 轨迹

- 完整复用 `utils/gpx.js parseGpx`：航点（wpt/rtept）优先、纯轨迹按里程采样（≤12 点）、
  自动补最近轨迹点的 `<ele>/<time>`、输出 GCJ-02 坐标与 track（≤200 点）。这些是已上线能力，零新代码。
- 流程（对齐编辑器既有模式）：「导入 GPX」→ `wx.chooseMessageFile`（聊天文件，8MB 上限）→
  解析 → 预览弹层（节点列表 + `N 个节点 · x km · 爬升 y m` 统计行）→ 确认 → 存为轨迹点组
  → 组展开 → 点任一节点进查询视图。
- `suggestions`（风险/装备预填）在 hub **不消费**——那是活动创建语义，这里只做天气查询，不预填表单。

### 7.4 平台隐私依赖（已知缺口，降级照旧）

`wx.chooseMessageFile` 是隐私接口，平台《用户隐私保护指引》**至今未声明「选中的文件」**，
真机上会直接 fail（编辑器同款问题，见 SYNC 2026-09-28/29 条目）。hub 照抄编辑器的降级：
- API 不存在 → 提示升级；
- fail 区分「用户取消 / 隐私未声明 / 其他」，隐私未声明时展示与编辑器一致的操作路径指引；
- 引导文案内嵌：「把 GPX 文件发到任意聊天，再点上面按钮选择」。
平台过审前，GPX 导入在真机上的预期行为就是"看到指引"，开发者工具内可用——与编辑器现状一致，
不阻塞本模块其余部分上线。

## 8. 云函数：新 action `getWeatherByPoint`

### 8.1 契约

```
请求  { action:'getWeatherByPoint', lat, lng, date }
校验  lat/lng 为有限数且在范围；date 过 validDateStr，距今天 0–14 天
响应  { status:'ready', updatedAt, days, detail, series, pointElevation }
    | { status:'out_of_range' }                                   // 超 14 天或 diff<0
    | { status:'unavailable', message }                           // 服务异常等
```

- 返回体形状与 `getWeather` 的 ready 分支**逐字段一致**（少一个遗留 `hours` 字段，
  客户端自 P2 起只消费 series/days/detail/pointElevation），查询视图两条路径共用同一装配函数。
- 不需要 `ele` 入参：海拔参与的是**客户端**天相计算（point.ele 优先、pointElevation 兜底），
  云函数只负责取数——与活动路径的分工完全相同。

### 8.2 实现

- `index.js`：`actionGetWeatherByPoint(payload)` ≈ `actionGetWeather` 去掉状态加载与节点定位，
  其余（validDateStr / 距离窗 / `gcjToWgs` / `getCachedForecast` / 返回体组装）逐段同构。
  两个 action 的公共段可提一个小函数，但不强行抽象——两处各自 40 行以内，可读性优先。
- **顺带的性能收益（初版漏写的卖点）**：`actionGetWeather` 每次查询都先 `store.loadState(db)`
  全量加载状态再定位节点——这正是当年 3 秒超时悬崖的成分之一；`getWeatherByPoint` 完全跳过
  状态加载，**自由查询比活动路径更快**。
- 免鉴权：`exports.main` 的 OPENID 闸门从 `event.action !== 'getWeather'` 改为
  `WEATHER_FREE_ACTIONS.has(event.action)`（含 getWeather 与 getWeatherByPoint）。
  天气是非个人数据，v1 起 getWeather 即免鉴权，此处沿用同一语义。
- **缓存共享是免费的**：`getCachedForecast` 的 key 是 `w_<lat.toFixed(2)>_<lng.toFixed(2)>_<date>`
  （约 1.1 km 网格）。从地图选点查的坐标若与某活动节点落在同一网格，30 分钟内直接命中同一份缓存；
  反之活动路径的查询结果也被自由查询复用。无新集合、无新缓存逻辑。

### 8.3 滥用边界（诚实记录）

免鉴权 + 免费上游意味着可被脚本刷。现有防线：坐标缓存网格 + Open-Meteo 30 分钟 TTL +
云函数自身 20s 上限。V1 **不做**每用户限流（getWeather 同样裸奔，风险面没有扩大）；
若上线后观察到刷量，再上"按 OPENID/设备每分钟 N 次"的轻限流——记录在此，避免将来当作新问题重新讨论。

## 9. Hub 页面结构（pages/weather-hub）

自上而下：

1. **页头**：eyebrow「天气」+ page-title「先看天，再上山。」
2. **输入区**：
   - 主按钮「地图选点查天气」（primary，唯一实心按钮——主行动唯一化）；
   - 次按钮行：「输入经纬度」（text/secondary）；
   - GPX 导入卡（对齐编辑器主路径卡样式）：标题 + 一句话收益（"导入轨迹，自动取出山路线上的标注点"）+「导入 GPX 轨迹」按钮 + 聊天操作引导内嵌。
3. **我的观察点**（有数据才显示；空态收起，不渲染空卡片——空态三件套规则）：
   每行 = 名称 + 坐标/海拔小字 + 「删除」文字按钮（dialog 二次确认）；点行进查询视图。
4. **轨迹点组**：收合式列表（沿用编辑器节点折叠样式）——折叠行 = 组名 + 统计摘要
   （N 个节点 · x km · 爬升 y m），展开 = 节点行（名称 + 第几天/时刻若有时间戳，取
   `RS.schedule(points, null)` 的「出发后 X 小时」相对标签，纯客户端零成本），点行进查询视图
   （`set` 入参，查询视图内按 §5.4 展开成基于基准日的抵达日）；组头部右侧「删除」。
5. 观察点与轨迹组**分开展示不混排**：来源与形态不同（单点 vs 行程序列），混排会让"点"
   的心智变糊。

- onShow 每次重读观察点/轨迹组列表（从查询页「保存此点」返回后立即可见，不靠手动刷新）。

全部交互遵循 ourtrail-ui skill：overlay 需 `styleIsolation: 'apply-shared'`、danger 操作
dialog 二次确认、状态用 status-panel、文案短句面向动作。
