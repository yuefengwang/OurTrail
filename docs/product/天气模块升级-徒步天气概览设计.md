# 设计文档：天气模块升级 P1——徒步天气概览

日期：2026-09-28（v2 定稿：云层方案改为气压层剖面 cloudBand，弃用 LCL 公式）
状态：已确认，按本方案实施
影响版本：V1（天气页 + 云函数天气代理）
相关模块：`cloudfunctions/trailApi/lib/weather.js`、`cloudfunctions/trailApi/index.js`（getWeather）、`miniprogram/pages/weather/`、`miniprogram/utils/gpx.js`（gcjToWgs）

---

## 1. 背景与目标

徒步圈习惯用 meteoblue 的 meteogram 查山：逐日条（温/风/降水/日照）+ 时序图（温度线、降水柱、云层高度带、云量）。用户希望把这套信息习惯带进小程序，其中**云层高度（云海/入云判断）是核心诉求**。

**决策：不嵌入 meteoblue，复刻信息架构。** 原因：个人主体小程序无 web-view 权限；meteoblue 图片按"署名回链"条款供站外使用，小程序内外链不可点、英文界面不可控、坐标单点；meteoblue API 收费，而现有数据源 Open-Meteo（免费非商用、无需 key）的变量库足以复刻——**且可以用与 meteoblue 同源的方法（模型垂直剖面）重建云层带**（§4.2）。

## 2. 现状与差距

现有链路（健康，保留）：详情页「天气参考」→ weather 页选节点+选日期 → 云函数 `getWeather` → Open-Meteo 代理 + 30 分钟缓存 → 8 个整点时段列表 → 组织者一键生成天气提醒草稿。

| meteogram 信息 | 现状 | 数据来源 | P1 |
|---|---|---|---|
| 逐日概览（高低温/风/降水/日照） | 无 | daily 10 变量（已逐一核验存在） | ✅ |
| 低/中/高三层云量 | 无 | `cloud_cover_low/mid/high` | ✅ |
| 云层高度带（云海核心） | 无 | **气压层云量剖面重建**（§4.2，与 meteoblue 同源方法） | ✅ |
| 温度线/降水柱时序图 | 干数字列表 | `showers` 与 `precipitation` 分开 | 摘要行（图 P3） |
| 日出日落/UV/冻结高度/能见度 | 无 | `sunrise/sunset/uv_index/freezing_level_height/visibility` | ✅ |
| 徒步语言（"垭口入云""早出发"） | 无 | 转译规则 §5.3 | ✅ 基础版 |

## 3. 接口契约（不变的部分）

`api.getWeather(activityId, pointId, date)` 签名、`status: 'ready' | 'out_of_range' | 'unavailable'` 三态、缓存 key 与 30 分钟 TTL 全部不变。返回体在现有 `hours` 之外新增字段：

```js
{
  status: 'ready',
  updatedAt: iso,
  hours: [...],              // 现有 8 时段列表，字段不变（保留兼容）
  pointElevation: 1167,      // Open-Meteo 返回的模型海拔（m ASL），云带判断基准（P1）
  days: [{                   // 7 日概览（自今天起），前端高亮所选日
    date: 'YYYY-MM-DD',
    code: 3, tMax: 15, tMin: 9,
    windMax: 11,             // km/h
    precipSum: 1.2, precipProbMax: 60, precipHours: 4,
    sunrise: '07:02', sunset: '19:46',
    uvMax: 8,
    cloud: { low: 62, mid: 10, high: 0 },   // 当日平均云量 %
  }],
  detail: [{                 // 所选日 24h 逐时扩展（分时段摘要 + P3 画图复用）
    t: '08:00',
    temp: 11, feels: 9, precip: 0.2, showers: 0, pop: 35,
    wind: 9, gust: 22,
    cloud: { low: 80, mid: 5, high: 0 },
    uv: 2,                   // 夜间为 null → 显示 '—'
    visibility: 18,          // km
    freezing: 4200,          // 0℃ 层海拔 m
    band: { base: 1800, top: 2600, cover: 92 },  // 云层带（m ASL），无云层为 null
  }],
}
```

## 4. 数据层设计（lib/weather.js）

### 4.1 请求参数

```js
hourly: 'temperature_2m,apparent_temperature,precipitation_probability,precipitation,showers,'
      + 'weather_code,wind_speed_10m,wind_gusts_10m,'
      + 'cloud_cover_low,cloud_cover_mid,cloud_cover_high,'
      + 'uv_index,visibility,freezing_level_height,'
      // 气压层云量剖面 + 层海拔（重建云层带用）：
      + 'cloud_cover_1000hPa,cloud_cover_975hPa,cloud_cover_950hPa,cloud_cover_925hPa,'
      + 'cloud_cover_900hPa,cloud_cover_850hPa,cloud_cover_800hPa,cloud_cover_700hPa,cloud_cover_600hPa,'
      + 'geopotential_height_1000hPa,geopotential_height_975hPa,geopotential_height_950hPa,'
      + 'geopotential_height_925hPa,geopotential_height_900hPa,geopotential_height_850hPa,'
      + 'geopotential_height_800hPa,geopotential_height_700hPa,geopotential_height_600hPa',
daily: 'weather_code,temperature_2m_max,temperature_2m_min,wind_speed_10m_max,'
     + 'precipitation_sum,precipitation_probability_max,precipitation_hours,'
     + 'sunrise,sunset,uv_index_max',
forecast_days: min(16, diff + 2)   // 现有动态算法保留
```

变量名已对官方文档核验；**响应键保留 hPa 后缀**（如 `cloud_cover_925hPa`，已用真实 API 调用确认）；日出日落为本地时间 ISO 无时区后缀（`2026-09-28T06:57`，取 `slice(11,16)`）。高海拔地点低层气压层可能位于地下返回 null，解析时跳过。

### 4.2 云层带：气压层剖面重建（关键决策，v2 定稿）

**弃用 LCL 经验公式**（125×(T−Td)+海拔）。该公式回答的是"地表气块受热抬升在哪里凝结"（晴天午后热力积云云底），在层云场景完全失灵——而**云海恰是层云场景**（山谷稳定湿层 + 山顶干爽，地表温露差大，公式会误判"无云"）。meteoblue 的云层带也不来自该公式，而是模型三维云量/湿度场的垂直剖面。

本方案与 meteoblue 同源：**Open-Meteo 提供逐气压层云量**（文档注明由相对湿度近似）+ 各层位势高度（官方说明用于换算海拔米数）。逐小时重建：

```js
// levels: 当小时全部非 null 的 { alt(位势高度 m ASL), cc(云量 %) }，按 alt 升序
// solid = cc ≥ 80 的层；band.base = 最低 solid 层海拔，band.top = 最高 solid 层海拔，cover = solid 层最大云量
// 无 solid 层 → band = null
```

- 近地面垂直分辨率约 250~600 米/层，判断"垭口在云里还是云上"足够；
- 判定阈值 80% 取"成层云"语义；50~80% 视为薄云/未成层，不入带；
- `pointElevation`（P1 用模型降尺度海拔；P2 换 RoutePoint 真实 ele，见 §9）与带比较：节点海拔落在带内 → 入云；带顶低于节点 → 有云海窗口。

### 4.3 返回体组装

- `days`：daily 全量（自今天起 ≤8 天），含当日平均云量（low/mid/high 逐时均值）；前端高亮所选日；
- `detail`：所选日期 24 小时全量，每小时含 band；夜间 uv 为 null 属正常；
- `hours`：维持旧逻辑（06-20 八个整点）输出，兼容；
- `out_of_range` 判定不变（>14 天）。

### 4.4 缓存

key/TTL 不变（`w_{lat}_{lng}_{date}` 0.01° 粒度 + 30 分钟）。体积评估：8 天 daily + 24h×33 变量 detail ≈ 60~100KB JSON，远低于云开发文档 512KB 限制；免费额度 10000 次/日充裕。

## 5. 展示层设计（weather 页）

### 5.1 页面结构（自上而下）

```
留意天气，也留意脚下。            ← 现有标题
[天气是行前参考，不是出发许可]     ← 现有免责 callout，保留
── 7 日概览条（横向滚动）──
 [周一 今] [周二] [周三] …
  多云      阵雨     阴           ← WMO code 简字徽标
  15/9℃    12/8℃   11/8℃
  ☂60%     ☂85%    ☂40%
── 当日徒步提示 callout（转译 §5.3，最多 2 条）──
── 分时段摘要（06-20 八行：时刻/短语/温度/降水/风）──
▸ 展开逐小时数据                 ← 原 24h 明细折叠
[路线关键点] [查看日期]           ← picker 保留（换节点/日期重查，30min 缓存内零成本）
数据来源 Open-Meteo.com (CC BY)  ← 署名，合规要求
[生成天气提醒草稿]               ← 组织者，保留
```

- 天气图标不引入图片资源：WMO code → 简字徽标（晴/少云/多云/阴/雾/雨/雪/雷暴），文字承载语义，符合项目设计语言；
- 7 日卡选中态 forest 描边，点击切日期重查。

### 5.2 转译规则（WMO code + 云层带 + 降水信号 → 徒步短语）

WMO code 映射（归口 `utils/format.js`）：

| code | 简字/tone |
|---|---|
| 0 | 晴 / success |
| 1-2 | 少云 / success |
| 3 | 阴 / neutral |
| 45,48 | 雾 / warning |
| 51-57 | 毛毛雨 / warning |
| 61-67 | 雨（强度分小/中/大） / warning |
| 71-77 | 雪 / danger |
| 80-82 | 阵雨 / warning |
| 85,86 | 阵雪 / danger |
| 95-99 | 雷暴 / danger |

当日提示 callout（按优先级最多 2 条）：

1. `code ≥ 95` → 「有雷暴概率，不建议安排上山」（danger）；
2. `code 71-77` 或 `freezing < pointElevation` → 「0℃ 层低于此点，降水可能为雪」（danger）；
3. `visibility < 1km` 或（`band` 且 `band.base ≤ pointElevation ≤ band.top`）→ 「此点可能入云（雾），观景窗口有限」（warning）；
4. **云海窗口**：`band` 存在 且 `pointElevation > band.top` 且 `band.cover ≥ 80` 且 `cloud.high < 30` → 「云海概率较大」（success）；
5. `precipProbMax ≥ 60` 且午后 `showers` 高 → 「午后阵雨概率高，建议早点出发」（warning）。

### 5.3 准确率定位（诚实预期，写入 UI 语气）

| 层次 | 能达到的准确度 |
|---|---|
| 天气尺度情景（有无低云/降水系统） | ~70-80%，模型强项 |
| 云层高度数字 | ±300~600 m（19 层采样 + RH 参数化所致） |
| 具体山谷、日出那一刻的云海 | **无产品能高准确率承诺**（含 meteoblue）：模式地形抹平山谷、层云/雾是 NWP 公认弱项、时间误差 ±3h 即成败 |

因此 UI 一律用概率语言（"云海概率较大"而非"有云海"），并且免责 callout 常驻。P2 通过多模型互验与合成指标提置信（§9）。

## 6. 顺手修复：坐标未纠偏

**既有缺陷**：库存坐标是 GCJ-02，直接喂给了要 WGS-84 的 Open-Meteo，偏移数百米。对气象格点影响可忽略，但坐标对齐是原则且成本一行：`utils/gpx.js` 增加 `gcjToWgs` 逆变换（局部线性反演迭代 2 次，误差 <1e-5°），`lib/weather.js` 查询前转换。含 node 往返精度测试。

## 8. 验收标准

1. 天气页顶部出现 7 日概览条，数据与 Open-Meteo 官网同坐标查询一致（抽查温度/降水/日出）；
2. 云层带字段真实产出（抽查山区坐标清晨时段 band 非空，海拔量级合理）；
3. 切换节点/日期正确刷新，30 分钟内命中缓存（云函数日志无重复外呼）；
4. 转译 callout 按规则出现（雷暴/降雪/入云/云海/阵雨各造一条数据走查）；
5. 组织者草稿按钮、免责 callout、picker 行为不变；署名 footer 可见；
6. gpx-test gcjToWgs 往返用例全绿；云函数 smoke 不回归；Open-Meteo 请求坐标为 WGS-84。

## 9. 范围外与后续预埋

- **P2·准确率增强包**：①多模型互验（Open-Meteo 免费多模型端点 ICON/GFS/ECMWF 同参查询，低云结论一致→高置信，分歧→明示"变数大"）；②云海窗口合成指标（前日降水/夜间晴空/微风/低层湿层/清晨时段五信号叠加，比单报云顶数字稳健）；③置信度文案分级。免费额度内 2-3 倍请求量，代理层隔离，前端不动契约。
- **P2·真实海拔联动**：RoutePoint schema 加可选 `ele`（RouteSnapshot/Route 同步加，流程同 track），GPX 导入时写入节点 ele，替换 `pointElevation` 的模型降尺度值。
- **P3（可视化）**：canvas 自绘温度线 + 降水双柱（precipitation/showers）+ 云层带色带。detail 结构已按画图需求设计，数据层无需再动。
- 商业化时数据源合规切换（和风/彩云），代理层已隔离。
