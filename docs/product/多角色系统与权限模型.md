# 多角色系统与权限模型

文档日期：2026-09-24  
状态：V1 产品实现路径共识  
适用版本：V1，并为 V2/V3 的认证与开放生态预留结构

---

## 1. 核心结论

产品采用：

> **一个微信小程序、一套账号和数据，根据用户的全局角色及其与具体活动、路线、车辆的关系，展示不同视角和操作。**

平台运营和审核能力独立为 Web 管理后台，不放在微信小程序中。

V1 不拆分多个小程序，不为参与者、领队、协作人员、车辆联系人分别提供独立 AppID。

---

## 2. 为什么采用一个小程序

### 2.1 用户身份天然重叠

同一个人可能同时是：

- 普通参与者；
- 某场活动的领队；
- 另一场活动的收队；
- 私家车车主或车辆联系人；
- V2 的路线贡献者。

如果拆成多个小程序，用户资料、历史活动、信用记录、通知和权限会被割裂。

### 2.2 活动协作需要同一套数据

一场户外活动至少可能涉及：

- 活动创建者；
- 报名者；
- 副领队、收队；
- 车辆联系人或司机；
- 紧急联系人。

这些角色围绕同一场活动协作，需要共享同一套活动、名单、节点和车辆数据。

### 2.3 降低早期使用门槛

微信用户更愿意从群聊或分享卡片直接进入具体任务，而不是下载、收藏并区分多个小程序。

### 2.4 降低早期开发和维护成本

多小程序会带来重复登录、重复数据同步、权限不一致、通知分裂和版本发布复杂等问题。

---

## 3. 两层角色模型

系统必须区分：

1. **全局角色**：用户长期拥有的身份或能力；
2. **活动关系**：用户在某一场具体活动中的临时关系和权限范围。

权限判断公式为：

```text
最终权限 = 全局角色 + 当前资源关系 + 资源状态 + 授权范围
```

其中“当前资源”可能是一场活动、一条路线、一辆车、一个车辆任务或一条路线反馈。

---

## 4. 全局角色

全局角色描述一个用户在平台内可被识别的身份。

### 4.1 V1 角色

| 全局角色 | 获得方式 | 是否需要认证 | 说明 |
|---|---|---|---|
| participant（参与者） | 默认拥有 | 否 | 所有微信用户的基础角色 |
| leader（领队） | 首次创建活动后自动解锁 | V1 不认证 | 可创建和管理私域活动 |
| staff（协作人员） | 被领队添加后获得 | 否 | 可在指定活动中承担协作任务 |
| vehicle_contact / driver（车辆联系人/司机） | 被领队添加或收到车辆任务后获得 | V1 不认证 | 可查看被分配的车辆任务 |

### 4.2 V2 扩展角色

| 全局角色 | 说明 |
|---|---|
| certified_leader | 提交资料并通过审核的领队 |
| route_contributor | 可上传和维护轨迹、路线、节点和反馈的用户 |
| certified_driver | 提交驾驶及相关资料并通过审核的司机 |
| provider | 租车公司、车队或车辆服务商 |

### 4.3 V3 扩展角色

| 全局角色 | 说明 |
|---|---|
| route_editor | 可在特定区域内编辑公开路线的高级贡献者 |
| club_admin | 俱乐部主页和成员管理者 |
| professional_org | 专业户外机构或组织主体 |

---

## 5. 活动关系

全局角色不能单独决定一场活动中的权限。用户在具体活动中还需要一条关系记录。

### 5.1 活动关系类型

| 活动关系 | 说明 |
|---|---|
| owner / organizer | 活动创建者、主负责人 |
| coleader | 副领队 |
| sweeper | 收队 |
| staff | 中队、志愿者或其他协作人员 |
| participant | 已报名参与者 |
| waitlist | 候补人员 |
| vehicle_contact | 本活动的车辆联系人 |
| driver | 本活动的司机 |
| cancelled | 已取消报名人员 |
| removed | 被领队移除的人员 |

### 5.2 关系中的权限范围

活动关系应记录更细的授权范围，例如：

- 可查看哪些人员；
- 可管理哪些节点；
- 是否可协助签到；
- 是否可上报异常；
- 是否可查看紧急联系人；
- 是否可导出名单；
- 是否可编辑路线或活动信息。

示例：

| 用户 | 全局角色 | 某活动关系 | 权限范围 |
|---|---|---|---|
| 林舟 | leader、participant | owner | 全场管理 |
| 小王 | participant | sweeper | 后队人员、节点打卡、异常上报 |
| 老陈 | driver、participant | driver | 本车乘车人、上车点和导航 |
| 张三 | participant | participant | 本人信息、自助签到、安全到家 |

## 6. V1 的四套用户视角

V1 原型和实现均拆成四套视角。

### 6.1 参与者视角

核心任务：

- 查看微信群分享的活动；
- 了解路线难度、集合点、上车点、天气和装备要求；
- 报名或帮同行人报名；
- 修改报名信息或取消报名；
- 查看分车结果；
- 活动当天自助签到；
- 活动结束后确认安全到家；
- 查看历史活动。

不可见内容：

- 完整报名名单；
- 其他人的手机号；
- 其他人的病史、过敏或紧急联系人；
- 活动编辑和全量管理功能；
- 与本人无关的车辆任务。

### 6.2 领队视角

核心任务：

- 创建、编辑、发布和取消活动；
- 设置路线、节点、风险点、下撤路线和上车点；
- 查看完整报名名单；
- 代报名、修改报名、取消报名、候补转正；
- 登记车辆、车辆联系人并执行分车；
- 添加副领队、收队和协作人员；
- 活动当天查看签到、节点、异常和安全到家状态；
- 发送订阅消息或复制微信群公告；
- 活动结束后复盘并沉淀路线实况。

V1 中活动创建者展示为“未认证领队”。

### 6.3 协作/收队视角

核心任务：

- 查看被分配负责的人员；
- 查看路线节点、风险提示和下撤路线；
- 协助签到；
- 记录节点通过；
- 上报掉队、受伤、身体不适、临时下撤等异常；
- 查看被授权范围内的紧急联系人；
- 协助确认安全到家。

该视角应显著简化，不提供全量活动编辑、全部名单、车辆配置等领队能力。

### 6.4 车辆联系人/司机视角

V1 先做轻量任务视图，V2 再升级为正式司机与车辆网络。

核心任务：

- 查看活动日期和车辆任务；
- 查看集合点、上车点及每个上车点人数；
- 查看本车乘车人的必要联系方式；
- 一键导航；
- 标记人员是否已上车；
- 联系领队；
- 确认返程或任务完成。

不可见内容：

- 参与者病史和过敏信息；
- 参与者紧急联系人；
- 完整活动报名名单；
- 活动编辑权限；
- 与本车无关的信息。

## 7. 推荐进入方式

V1 不展示启动时角色选择页，不要求新用户先回答“你是谁”。

进入策略为：

> **默认参与者视角 + 场景自动进入对应任务 + 用户手动切换。**

### 7.1 默认参与者视角

用户直接打开小程序时，默认进入参与者首页，展示：

- 我报名的活动；
- 最近从微信群打开的活动；
- 历史活动；
- 弱化的“发起活动”入口。

### 7.2 首次创建活动后解锁领队模式

用户点击“发起活动”并成功创建后：

- 自动添加 leader 全局角色；
- 自动进入该活动的领队管理上下文；
- 后续可在参与者模式和领队模式之间切换；
- 活动详情中仍显示“未认证领队”，直到 V2 完成认证。

### 7.3 协作人员从任务链接直达

当用户被添加为副领队、收队或协作人员，通过群聊或通知打开对应链接时，系统自动进入协作任务视图。

重点展示：

- 我负责的人员；
- 节点与风险提示；
- 异常上报；
- 被授权的紧急信息。

### 7.4 车辆联系人从车辆任务链接直达

车辆联系人打开领队分享的任务链接时，系统自动进入车辆任务视图，不要求其先浏览小程序首页或寻找入口。

重点展示：

- 行程安排；
- 上车点；
- 本车乘车人；
- 导航和上车确认。

### 7.5 手动切换

拥有多个角色的用户可以手动切换：

- 参与者模式；
- 领队模式；
- 指定任务模式。

即使用户是领队，也可以回到普通参与者视角，避免管理功能长期干扰普通使用。

## 8. 页面复用策略

系统不要求为每个角色完全重写页面。同一页面可以根据角色、活动关系和权限加载不同模块。

### 8.1 活动详情页模块示例

| 模块 | 参与者 | 领队 | 协作/收队 | 车辆联系人 |
|---|---|---|---|---|
| 活动简介 | 显示 | 显示 | 显示 | 显示 |
| 路线概览 | 显示 | 显示 | 显示 | 简版 |
| 节点信息 | 显示 | 可编辑 | 可打卡 | 仅任务相关点 |
| 上车点 | 显示本人相关点 | 全部 | 分管范围 | 全部任务点 |
| 报名名单 | 不显示 | 全部 | 分管人员 | 本车人员 |
| 风险提示 | 显示 | 可编辑 | 显示 | 简版 |
| 紧急联系人 | 仅本人 | 全部 | 授权范围 | 不显示 |
| 管理入口 | 不显示 | 显示 | 简版 | 不显示 |

### 8.2 复用原则

- 通用信息模块尽量复用；
- 涉及权限和数据写入的模块独立封装；
- 前端组件只负责展示和交互，不承担最终安全判断；
- 云函数统一校验身份、活动关系和资源状态。

## 9. 技术实现建议

### 9.1 建议的数据对象

#### User

- openid；
- 基础资料；
- 手机号；
- 默认角色；
- 当前视角；
- 创建时间。

#### UserRole

- 用户 ID；
- 角色类型；
- 状态；
- 是否认证；
- 认证时间；
- 过期时间；
- 审核状态。

#### ActivityMembership

- 活动 ID；
- 用户 ID；
- 活动关系；
- 权限范围；
- 状态；
- 创建人；
- 创建时间；
- 失效时间。

#### ResourcePermission

用于记录用户对路线、车辆、车辆任务、名单导出等资源的权限：

- 资源类型；
- 资源 ID；
- 用户 ID；
- 权限动作；
- 授权范围；
- 过期时间。

### 9.2 云函数统一鉴权

前端隐藏按钮只用于体验，不能作为安全边界。

所有关键操作必须在云函数中重新校验：

```text
接收请求
   ↓
识别用户 OpenID
   ↓
读取用户全局角色
   ↓
读取用户与当前活动/路线/车辆的关系
   ↓
检查资源状态和授权范围
   ↓
允许或拒绝操作
```

需要云函数鉴权的典型操作：

- 查看完整名单；
- 导出名单；
- 修改或取消活动；
- 查看紧急联系人；
- 分车和调整车辆；
- 签到和节点打卡；
- 异常上报与处理；
- 查看车辆任务；
- 添加协作人员。

### 9.3 权限拒绝

当用户通过旧链接、他人转发或直接访问无权限页面时，应展示：

- 当前身份；
- 无法访问的原因；
- 可联系的领队或活动创建者；
- “返回我的活动”入口；
- 必要时提供申请访问或重新登录入口。

## 10. 原型拆分计划

角色原型独立存放：

```text
docs/prototypes/roles/
├─ participant.html       参与者原型
├─ leader.html            领队原型
├─ staff.html             协作/收队原型
├─ driver.html            车辆联系人/司机原型
└─ role-switch-map.html   角色切换与权限关系图
```

每套角色原型至少包含：

- 角色首页；
- 核心任务路径；
- 空状态；
- 异常状态；
- 无权限提示；
- 隐私授权说明。

## 11. 分阶段实施顺序

### V1.0：参与者 + 领队

- 参与者报名；
- 领队创建与管理活动；
- 活动分享；
- 自助签到；
- 安全到家。

### V1.1：协作人员

- 领队添加收队/副领队；
- 协作人员查看分管名单；
- 协助节点打卡和异常上报。

### V1.2：车辆联系人

- 领队添加车辆联系人；
- 车辆联系人查看本车任务；
- 上车点导航；
- 上车状态确认。

### V2.0：认证与网络化

- 领队认证；
- 司机认证；
- 车辆资质；
- 供应商认证；
- 路线贡献者身份。

### V3.0：开放生态

- 公开活动；
- 公开路线；
- 俱乐部主页；
- 服务商网络；
- 平台运营治理体系。

---

## 12. 关键边界

- V1 允许任何人创建私域活动，但不提供公共流量推荐；
- V1 不做在线支付、退款、保险、发票或合同；
- V1 不做派单和承运承诺；
- V1 不承诺救援；
- V1 不做完整聊天系统；
- 敏感信息必须按角色、活动关系和时间范围授权；
- 平台运营后台与微信小程序分离。

---

## 13. 成功标准

多角色系统在 V1 的成功不是角色数量多，而是：

- 参与者能清楚完成报名、查看集合安排和确认安全到家；
- 领队能显著减少微信群反复确认、名单错误和分车沟通；
- 协作人员能在被授权范围内完成少量关键操作；
- 车辆联系人能快速理解任务、名单、上车点和导航；
- 所有角色都围绕同一场活动共享一致数据。
