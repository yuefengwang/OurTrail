# 户外组队与路线基础设施：产品愿景与版本路线图

文档日期：2026-09-24  
状态：产品共识初稿  
适用项目：微信小程序「山野同路」（当前目录名：outoutout）

---

## 1. 产品定位

这不是一个单纯的活动报名工具，而是面向徒步、登山、露营、亲子户外等场景的组队与履约基础设施。

长期目标是连接：

- 普通户外参与者；
- 领队、副领队、收队、协作人员；
- 私家车主、商业司机；
- 租车公司与车辆服务商；
- 路线贡献者、审核者和平台运营者；

并围绕户外活动沉淀五类核心资产：

1. **人的资产**：身份、经验、能力、信用、领队资质、司机资质；
2. **路线资产**：轨迹、节点、风险点、下撤路线、集合点、实际通行反馈；
3. **交通资产**：车辆、司机、服务商、上车点、价格、评价和资质；
4. **履约数据**：报名、审核、分车、签到、节点通过、异常、安全到家；
5. **环境数据**：路线分段天气、季节、封路、塌方、积雪、管制和历史反馈。

---

## 2. 长期愿景

> 成为用户、领队、司机共同使用的户外活动基础设施，并维护一张持续更新、可信、可复用的户外路线图。

平台希望解决的长期问题包括：

- 活动组织高度依赖熟人和领队个人经验；
- 报名、分车、签到、安全确认分散在微信群、表格和口头沟通中；
- 路线轨迹、风险点、下撤路线无法稳定传承；
- 天气信息通常只看城市，不看路线节点和海拔；
- 租车、司机、上车点、乘车名单之间缺少统一协作；
- 活动结束后的真实路况、耗时、风险反馈容易流失。

---

## 3. 核心业务闭环

```text
路线资料库
   ↓
选择路线 / 复用历史活动模板
   ↓
发布活动 → 用户报名 → 领队审核
   ↓
拼车 / 租车 / 车辆与司机协作
   ↓
集合签到 → 节点打卡 → 异常与安全状态管理
   ↓
活动复盘 → 更新路线实况、评价人员与车辆
   ↓
反哺路线资料库
```

这个闭环的关键不是单次活动，而是每一次活动都能让路线、人员、车辆和风险数据变得更完整。

---

## 4. 角色定义

| 角色 | 核心诉求 |
|---|---|
| 普通参与者 | 找活动、了解路线难度、报名、查看集合安排、车辆、天气和通知 |
| 领队/组织者 | 快速发布活动、筛选人员、管理名单、安排交通、掌控现场安全 |
| 副领队/收队/协作 | 查看分工、管理部分队伍、记录节点和异常状态 |
| 私家车主 | 发布空座、确认同行人、查看上车点和导航 |
| 商业司机 | 查看订单、集合点、乘车名单、联系方式、导航和签到状态 |
| 租车/车辆服务商 | 接收用车需求、报价、安排车辆和司机、维护资质 |
| 路线贡献者 | 上传轨迹、标注风险点、补充照片和实际通行情况 |
| 路线审核者/平台运营 | 审核路线、处理纠错、认证领队与服务商、发布风险公告 |
| 紧急联系人 | 在必要场景下获得有限的应急信息 |

同一个自然人可以拥有多个角色。例如，一个用户可以同时是参与者、领队、路线贡献者和私家车主。

## 5. 产品设计原则

### 5.1 安全和隐私优先

- 医疗信息、紧急联系人、实时位置属于敏感信息；
- 实时位置应当限时、授权、按活动范围使用；
- 平台默认最小化收集和展示；
- 不把位置共享做成长期社交追踪；
- 所有敏感操作需要明确告知用途和可见范围。

### 5.2 先服务熟人场景

早期不追求公开广场，而是先服务微信群、俱乐部和固定领队圈子。这样可以降低内容审核、陌生人交易和纠纷成本。

### 5.3 路线是长期资产

活动可以结束，但路线轨迹、实际耗时、风险点、照片、下撤路线和交通可达性应被保留并版本化。

### 5.4 不承诺救援

平台提供信息整理、应急资料展示、位置签到和事件记录，但不能把产品表达为官方救援服务。

### 5.5 交易能力渐进开放

- V1：纯工具/数据层；
- V2：撮合与预约协作层；
- V3：在资质、客服、合规能力成熟后，再评估完整交易层。

### 5.6 微信群是早期沟通渠道

V1 不做完整聊天系统，继续利用微信群沟通；平台只承载结构化信息、关键状态、通知和资料沉淀。

## 6. 交易边界

| 层级 | 平台职责 | 是否进入版本 |
|---|---|---|
| A. 纯工具/数据层 | 报名、名单、路线、车辆信息、分车、签到、天气、通知文案 | V1 |
| B. 撮合与预约层 | 匹配领队、司机、车辆，管理报价、预约、资质、评价 | V2 起谨慎进入 |
| C. 完整交易层 | 支付、退款、客服、发票、保险、合同、承运资质和纠纷处理 | V3 视资质与运营能力决定 |

早期产品结构为 B 预留数据接口，但不在 V1 介入资金和承运责任。

## 7. 三版路线总览

### V1：熟人活动履约工具

**目标：**让领队在微信群场景中，把活动组织从手工表格和反复沟通中解放出来。

**核心能力：**

- 活动创建、编辑、状态管理；
- 报名、代报名、候补/取消/修改；
- 名单、问卷、导出；
- 上车点、车辆、自动分车；
- 集合签到、节点打卡、异常上报、安全到家；
- 关键点天气；
- 订阅消息和复制通知文案；
- 建立轻量路线数据结构。

**关键结果：**少出错、省时间、名单清楚、车辆安排清楚、安全状态可追踪。

详见：[V1 熟人活动履约工具](./V1-熟人活动履约工具.md)

---

### V2：路线与交通协作网络

**目标：**从单次活动工具升级为路线驱动、司机和车辆参与协作的网络。

原讨论中的 V1.5「路线驱动的活动策划」并入 V2，作为 V2 的第一阶段。

**核心能力：**

- 路线库、轨迹导入、路线版本和风险点；
- 从路线一键生成活动；
- 路线分段天气和路线状态反馈；
- 领队认证；
- 司机、车辆、供应商资料与资质；
- 商业租车需求、报价、任务确认；
- 司机视角和乘车签到；
- 熟人空座匹配；
- 活动复盘、评价和信用记录。

**关键结果：**路线可复用、交通可协作、领队/司机/车辆可信，活动数据持续反哺路线库。

详见：[V2-路线与交通协作网络](./V2-路线与交通协作网络.md)

---

### V3：开放的户外路线基础设施

**目标：**建设由社区和认证伙伴共同维护的户外路线地图，并形成开放的活动、交通和服务生态。

**核心能力：**

- 公开路线地图与社区贡献；
- 路线状态实时反馈；
- 公开活动、俱乐部主页和服务发现；
- 领队、司机、服务商生态；
- 开放接口和数据服务；
- 完整信任、安全和治理体系；
- 在合规前提下评估支付、保险、发票等交易能力；
- 智能推荐、风险评估和路线规划能力。

**关键结果：**路线成为平台网络资产，平台成为户外活动组织和履约的基础层。

详见：[V3-开放的户外路线基础设施](./V3-开放的户外路线基础设施.md)

## 8. 当前 Demo 与目标版本的关系

| 领域 | 当前 Demo 已有基础 | 后续重点 |
|---|---|---|
| 活动 | 创建、编辑、状态、模板 | 与路线库联动、审核、发布范围 |
| 报名 | 自助报名、代报名、取消、修改、名额事务 | 资格校验、候补、身份与信用 |
| 名单 | 名单查看、导出、应急信息 | 隐私分级、标签、历史记录 |
| 交通 | 车辆管理、自动分配、上车点 | 司机端、供应商、资质、报价 |
| 当天 | 签到、节点打卡、异常上报、安全到家 | 协作角色、现场流程、路线偏离提示 |

| 治理 | 暂无 | 审核、举报、封禁、运营后台 |

## 9. 初步北极星指标

可考虑将 V1 的北极星指标定义为：

> 每周被完整履约的活动数，即完成「创建活动 → 报名 → 分车/集合 → 节点或签到 → 安全到家」闭环的活动数量。

辅助指标：

- 领队创建并发布活动所需时间；
- 活动当天名单错误率；
- 分车和上车点调整次数；
- 签到率与安全到家确认率；
- 活动结束后路线反馈提交率；
- 领队次月留存；
- 每个活跃领队每月组织活动数。

## 10. 待继续确认的问题

1. V1 是否只服务微信私域分享，不提供任何公开活动列表；
2. 第一批种子用户是固定俱乐部、职业领队还是松散熟人圈；
3. 路线数据由平台少数人维护，还是允许领队先贡献、平台审核；
4. 商业租车在 V2 中只做信息和预约，还是允许线上支付；
5. 是否需要独立的司机端页面，或让司机使用同一个微信小程序角色视图；
6. 活动费用、保险、免责声明、位置隐私的法律与合规文本需要专业审核。
