# 设计文档：天气模块升级 P2 —— 天相判断与 meteogram

日期：2026-09-28
状态：已实现
前置：[天气模块升级-徒步天气概览设计.md](天气模块升级-徒步天气概览设计.md)（P1 徒步天气概览，其 §9 的 P2/P3 本轮落地）
影响模块：天气页、路线节点数据模型、云函数天气代理

---

## 1. 背景与问题

P1 把天气页从"干数字列表"升级为"7 日概览 + 徒步提示 + 云海与日照卡"，解决了"看得到数字"。但两件事没解决：

**问题一：天相缺席。** 对户外而言，云海、日出、夕阳、星空、银河、彩虹、光染（俗称日照金山）这些才是"值不值得出发"的判断依据，而徒步圈判断它们靠的是经验——低云少才有光染、中高云有才能被染色、云带底低才压得住、观察点要高过云带顶。P1 的云海卡只用了其中两条信号，其余五类天相完全没有。用户明确反馈：图（meteoblue）里"上面是客观指标、下面是结论"的那套结构，才是徒步者实际使用的方式。

**问题二：没有时间坐标。** P1 的分时段摘要是 8 个固定时点的列表，看不出过程。meteoblue 的核心是 meteogram——温度曲线、降水柱、云量色带沿时间轴铺开，夜间底色区分。对徒步者来说关键信息是**"这个点什么时候会下雨、云什么时候压过来、我几点经过"**，列表结构表达不了。

**问题三：节点与日期对不上。** 徒步者看天气是按"走到哪个标注点、什么时候到"判断的。P1 的天气页只能整体选日期，无法回答"我在第 2 天的那个垭口是什么天气"。

## 2. 目标与非目标

**目标**

1. 天相结论：日照金山 / 云海 / 星空 / 银河 / 彩虹 / 晨昏光窗口六类，每条给结论 + 依据 + 往哪看 + 时段。
2. meteogram：横向可滚动的 7×24 小时时间坐标图，客观指标与结论分区呈现。
3. 按轨迹标注点推算抵达日：节点带"第几天抵达"，日期自动对齐，轨迹无时间信息时明确降级。
4. 天相判断使用节点真实高程，替代模型降尺度海拔。

**非目标**

- 不做多模型互验（理由见 §4）。
- 不做逐 10 分钟预报（免费额度与包体不划算，1 小时对徒步决策够用）。
- 不做实况（Open-Meteo 免费版无实况）。
- 不做"明天 vs 今天更热的穿衣建议"这类泛生活化内容（不是本产品的语气）。

## 3. 信息架构

按用户要求，页面分成两段：**上面客观指标，下面结论**。

```
免责 callout（常驻）
节点选择器（带"第2天 14:20"标注）+ 日期来源说明

── 客观指标 ──
7 日概览条（含每日日出）
meteogram（天相窗口标记 / 温度线 / 降水双柱 / 三层云量 / 天气简字 / 日时轴）
数字指标卡（日出日落 / 天文暗夜 / 三层云量 / 云层带高度 / 月相）
安全提示 callout（雷暴/降雪/入云/午后阵雨，与天相分开）

── 结论 · 天相 ──
6 张结论卡：晨昏光窗口 / 日照金山 / 云海 / 星空 / 银河 / 彩虹
  每张：标题 + 置信徽标 + 结论与依据 + 往哪看 + 时段
分时段摘要（保留）
逐小时明细（折叠，保留）
```

一个刻意的取舍：P1 的"云海与日照"卡既报数字又下结论，与新的云海卡重复且口径更粗，本轮收成**纯数字卡**（判断只在天相卡里给一处），避免两处结论打架。

## 4. 置信分级：单模型 + 三级文案，不做多模型互验

P1 §9 提过"多模型互验（ICON/ECMWF）"。本轮**不做**，理由：

- 云函数执行超时上限 20 秒，天气链路已占大半（状态加载 + 扩参外呼 + 缓存写入）。并发多模型把请求量抬到 2–3 倍，正好踩在悬崖上。
- 免费额度下多模型高频调用不可持续，而这个功能的实际使用频率是"行前看几次"，不是高频。
- 收益有限：天相判断里权重最大的信号是**云层结构**（气压层剖面），而单模型之间低云的差异远小于"云带底高 vs 观察点海拔"这个量级的差距。多模型能消掉的不确定性，量级上小于我们引入的判断误差。

改为按信号强弱给三级文案（条件较好 / 条件一般 / 条件较差）并附分数，让用户自己判断该信几分。后续若要提准确率，优先做 §9 的"多信号合成 + 置信分级"，而不是堆模型。

## 5. 天文层（utils/astro.js）

天文计算全部在客户端做，纯函数、可 node 测试。选 NOAA Solar Calculator 低精度式（误差约 ±2 分钟），够做概率判断。

| 能力 | 说明 |
|---|---|
| 太阳赤纬与均时差 | NOAA 分数年公式，只需年内第几天，不依赖儒略日 |
| 任意时刻太阳位置 | 高度角 + 方位角（自北顺时针）。方位角用 atan2 式——acos 式在太阳接近天顶时溢出 |
| 日出日落 | 含蒙气差（-0.833°）与**海拔俯角修正**，3500 m 处日出早约 9 分钟 |
| 三重暮光 | 民用 -6° / 航海 -12° / 天文 -18°，决定星空与银河窗口 |
| 黄金与蓝调时刻 | 黄金 0°→6°，蓝调 -6°→-4° |
| 月相 | 月龄、照亮百分比、八相名（原有，保留） |
| 银心季节与方位 | 季节 3–10 月；方位按北纬 25–40° 经验曲线给"往哪看"，**不是星历** |

时间基准：全站固定 UTC+8（中国无夏令时），不查时区库。

## 6. 天相转译（utils/sky.js）

每类天相 = 一组信号 → 0–100 分 → 三级文案 + 依据 + 方向 + 时段。信号与阈值都写在这里，便于按真机观感调。

| 天相 | 信号 | 方向怎么给 |
|---|---|---|
| 日照金山（光染） | 晨昏窗口（日出后/日落前 50 分钟）内 + 低云少（光能到山体）+ 中高云有（被染色）+ 无降水 + 观察点在云带上方 + 走向朝对侧 | 晨朝东至东北、昏朝西至西北；走向用轨迹前后节点连线求方位角，**明确标注"按轨迹走向估算"** |
| 云海 | 五信号：低层有云带（底 ≤2200 m）/ 观察点在带顶之上 / 清晨高层云少 / 清晨微风 <15 km/h / 前日有降水 | 站在此点向低处与远处看云顶 |
| 星空 | 天文暗夜窗口 + 暗夜晴空率（高中层云 <30% 且无降水）+ 月照（<25% 加满，≥70% 不加） | 关灯、避光害、开阔北向视野 |
| 银河 | 银心季 + 暗夜晴空率 + 月照，取云最少的一小时为推荐时段 | 该钟点的银心方位（经验曲线） |
| 彩虹 | 太阳高度 <40°（主虹在反日点 42° 半径）+ 降水或高湿 + 窗口长度 | 反日点方位 + 主虹顶部仰角 = 42° − 太阳高度 |
| 晨昏光窗口 | 无信号，客观时刻 | 日出日落、黄金、蓝调的具体钟点 |

**逐小时标记与结论卡共用同一套阈值**，避免图上标记与文字结论互相打架。

**一个关键取舍**：与太阳位置相关的标记（光染/黄金/蓝调）按**天文时刻窗口 + 整点相交**判定，不用"该整点的太阳高度角"——黄金时刻只有二十来分钟，整点采样会整段漏掉（例：日出 06:09 → 窗口 06:09–06:59，里面一个整点都没有）。彩虹用高度角判定是安全的（窗口宽达数十度）。

## 7. meteogram 组件

canvas 2d 自绘，`scroll-view` 横向滚动，168 列 × 22 px ≈ 3.7k px 宽。

| 行 | 高度 | 内容 |
|---|---|---|
| 天相窗口 | 20 | 连续同 key 的小时合并成圆角条并写标签（云海/光染/彩虹/星空/银河/黄金/蓝调） |
| 温度 | 46 | 折线 + 面积，每 3 小时与极值标数值，左轴标极值 |
| 降水 | 32 | `precipitation` 与 `showers` 双柱分色，不透明度随降水概率 |
| 云量 | 18 | 高/中/低三条细带，透明度随云量；成层云带另加底部实心标记 |
| 天气简字 | 18 | 每 3 小时一次，WMO code → 简字 |
| 日时轴 | 26 | 每日"周X M/D"，每 6 小时刻度 |

背景层：夜间底色按**逐日**天文暮光判定（不是固定色块，高纬度与季节都会让白昼长短变化很大）；所选日叠一层高亮带与左边线。

交互：点图上某小时 → 通知页面切到那一天。

## 8. 按节点推算抵达日

**核心判断：GPX 里的绝对日期无意义**（那是某次历史记录），有意义的是**相对出发点的耗时**。所以只取时间差，再以活动出发时刻展开——抵达钟点自然就是出发钟点。若把 GPX 日期当活动日期，多日行程会整体错位一天。

```
elapsed(i)  = time(i) − time(第一个有时间的节点)
arrive(i)   = startAt + elapsed(i)
dayIndex    = 自然日之差 + 1
```

页面日期优先级：**用户手动选 > 节点推算抵达日 > 入口带入 > 活动出发日 > 今天**。节点推算比详情页带过来的活动出发日更精确——多日行程里到某节点往往是第 2、3 天。

**数据来源的坑**：具名航点（`wpt`/`rtept`）通常没有 `<time>`/`<ele>`，只有 `trkpt` 有，而具名航点恰恰是用户对照天象的锚点。gpx.js 增加最近轨迹点匹配补齐，误差等于轨迹采样间隔（秒到分钟级）。没有这一步，需求 3 在最常见的导出格式下完全失效。

**降级**：轨迹里没有时间信息的节点给不出提醒，直接标"无时间信息"，**不按距离插值编造**。活动未定出发时刻时只给相对耗时不给日期。

**海拔的真实价值**：`ele` 不只是显示。云层带/云海/光染判断此前用 Open-Meteo 模型降尺度海拔（±300–600 m），换成真实高程后"此点在云上还是带内"的判断显著更准。缺 `ele` 时退回模型值并在界面标注来源。

## 9. 数据层改动

| 位置 | 改动 |
|---|---|
| `RoutePoint` | 加**可选** `time`（ISO instant）与 `ele`（-500..9000 m）。`RouteSnapshot`/`Route` 共用同一 spec，strict 模式下必须同加，此处天然满足 |
| `selectors.pointView` | 统一投影，缺省不带键（客户端据此判断能否推算）；`discoverView` 保持窄投影不外泄 |
| `editor` | `fromView` 带进表单、`buildInput` 带出命令——**必须原样透传**，否则编辑一次草稿就把 GPX 元数据静默抹掉 |

| `lib/weather.js` | `hourly` 增 `relative_humidity_2m`（彩虹与雾的水分信号，降水为 0 时高湿仍可能有虹或雾） |

## 10. 窗口内复用：切日不外呼

`series` 自带 7 天逐时数据。天气页缓存最近一次返回体并记 `pointId`，只要目标日期落在窗口内，切日/切节点**完全不外呼**，detail 在客户端按日切出。云函数 30 分钟缓存本来也让重复查询零成本，但这里连等待与状态切换都没有——图上连点七天看趋势应当是即时响应。

## 11. 性能与包体

- 天文计算：7 天 × `sunTimes` + 168 × `solarPosition` ≈ 200 次三角函数，< 5 ms。
- 天相标记：7 天 × `hourMarks`（每 24 h 一次 solarPosition）。
- canvas 每列 22 px 绘制 168 列，无渐变与阴影，单次 draw 在 10 ms 量级；`observers` 只在数据变化时重绘。
- 新增两个 util（astro/sky）与一个组件，无第三方依赖。

## 12. 准确率与话术边界（UI 强制约束）

| 天相 | 能给什么 | 不能给什么 |
|---|---|---|
| 云海 | 情景判断 70–80% | 具体山谷的海拔、具体日期的成云与否 |
| 日照金山 | 光染概率与大致时段 | 哪座山、几点几分、山体是否遮挡 |
| 星空/银河 | 暗夜窗口与晴空率 | 肉眼能见多少颗星、银河清晰度 |
| 彩虹 | 概率与反日点方位 | 一定会出现、有几道 |

- 文案一律概率语气（"有…的可能"、"概率较大"），禁止断言式（"会有云海"）。
- 免责 callout 常驻，并注明"云层与云海为模型推算"。
- 高度角误差：Open-Meteo 降尺度 ±300–600 m；节点用了 GPX 高程时显著更准。
- 银心方位与云海是经验模型，不是星历与数值预报。

## 14. 验收标准

- 节点选择器显示"（第2天 14:20）"，切节点时日期自动跟到该节点抵达日。
- 轨迹无时间戳的节点显示"无时间信息"，不编造。
- meteogram 横滑能看到 7 天、夜间底色正确、点图上某天即切日且无等待。
- 图上天相窗口标记与文字结论一致（同源阈值）。
- 六张结论卡都有依据与"往哪看/时段"，无数据时降级文案可读。
- 全部脚本测试通过（astro 60 / sky 65 / route-schedule 41 / gpx 47 / weather-page 35 / smoke 86 / check / check-handlers）。
- 真机重点看：canvas 首帧是否正常、dpr 缩放、7 日概览条与图窗口对齐。

## 15. 后续预埋

- 云端缓存键目前含日期（`w_lat_lng_date`），同一地点存 7 份重复预报。改成按地点缓存 + 服务端切 7 日窗口可省 7 倍存储与外呼，需重新部署才能验证，本轮未做（客户端窗口内复用已经消掉了用户可感知的延迟）。
- 节点真实海拔已通；下一步可做"按海拔微调气温"（每 100 m 约 0.6°C 的直减率）给徒步体感参考。
- 多日行程的逐日"窗口叠加视图"（把 7 天画成 7 条曲线）暂不做，当前 7 日条 + 单日图已够。
- 银河与星空的更细判据（大气透明度、银河带高度角范围）需要外部数据源，暂不做。
