# 天气模块升级 · P4 时空天相与漫游设计

> 状态：**设计已定稿，待落地**（原型在 `Weather Module Redesign/`，未提交）
> 前置：P1 徒步天气概览 / P2 天相与 meteogram / P3 独立天气模块
> 本文档既是设计规格，也是**迁移方案**——把 Figma Make 原型的设计语言搬进 `miniprogram/`，并给出复用/新增边界。

---

## 1. 背景与目标

P1–P3 解决的是「查得到天气」：选点、导入 GPX、拿 7×24 小时预报、给出天相结论卡。缺的是**空间与时间的一体化表达**——用户真正要回答的问题是：

> 「我 05:40 从山脚出发，14:10 站上 3900m 观景位；一路上什么时候云在脚下？哪一段是徒步？」

现有 `meteogram` 是**时间 × 数值**的横轴图，能标天相窗口，但看不出海拔，看不出路线起伏，也看不出「云底 1858m 低于我 3900m」这件事。P4 补上这一层。

**目标**

1. 一张图同时承载时间、海拔、云层、路线、天相五层信息。
2. 单一数据源驱动全模块，消除此前出现的口径矛盾。
3. 保留可漫游（拖动/播放）能力，让用户能"走一遍"这一天。
4. 留宿场景可延伸到夜间，呈现晚霞与银河窗口。

**非目标（明确不做）**

- 不做逐小时爬升速率推算（12 个采样点不足以支撑，见 §3.3）。
- 不做实时实况接入，仍是 Open-Meteo 预报。
- 不做救援/保险类承诺文案（沿用反模式 12）。
- 不改云函数协议：仍走 `getWeather` / `getWeatherByPoint`，本轮纯客户端。

## 2. 设计决策

### 2.1 已定

| # | 决策 | 理由 |
|---|---|---|
| D1 | 时空图 **X=时间、Y=海拔** | 路线爬升是徒步天气的第一语境；X=里程会丢掉"几点在山上" |
| D2 | 节点天相**内嵌在轨迹带里**，不再单列节点列表 | 避免同一信息出现两次 |
| D3 | 指标卡与结论卡**合并为一张**，结论给分并可展开理由 | 「有结论但不知道为什么」等于没结论 |
| D4 | 轨迹段用**渐变**而非纯色 | 12 节点 11 段，段内天相可能变化，纯色会骗人 |
| D5 | 播放头**默认停在起点** | 到达点已有虚线+标签双重标记，播放头再压上去是噪声；首屏应展示全程 |
| D6 | 「到达」徽标走**流内布局**，不用绝对定位 | 外层日期条是 `overflow-x:auto`，纵向亦裁切；且 46px chip 内绝对定位必然与居中图标相撞 |
| D7 | 留宿作为**显式开关**，时间轴延到 23:00 | 留宿是产品决策，不该由代码猜测；月亮时刻 18 是天文事实 |
| D8 | 保留 P3 的三种入口（地图/经纬度/GPX）与本地观察点 | 不动已上线能力 |

### 2.2 已定：主窗口与孤立点如何取舍

原型数据里 `14:10` 落在主窗口之外，是一座"孤立云海"——全线路仅此 1 个节点成立。

**决策：取方案 b —— 两者都陈述，按可信度分层。**

- 主窗口 `07:55–11:15`（6 节点）占主位，作为结论卡的主线。
- 孤立点 `14:10` **单列一行**，并注明「仅 1 个节点 / 空窗段 05:40–07:10、12:00–13:05 / 云量抬升 / 天相中断」。

理由：只讲主窗口会丢掉「14:10 那一刻确实站在云海里」这个真实且有情绪价值的信息；降级为脚注等于否认它。分层陈述既不误导，也不浪费。

**对契约的约束**（实现必须遵守）：

- `runsOf()` 仍需优先返回**多节点**段作主窗口；单节点段不得被当作主窗口。
- `nodeFacts()` 对孤立节点必须输出**独立的** `isolated: true` 标记与单独的理由串，不得与主窗口理由合并。
- 结论卡必须能同时渲染「主窗口」与「孤立点」两个区块，文案层级分明。
- 所有天气派生文案遵守 §4.4 概率语气。

### 2.3 本轮交付范围

**决策：期 1 → 期 6**（token 提升 → 数据层 → 几何层 → 时空图组件 → 漫游滑块 → 留宿与夜间天象）。

## 3. 数据模型（单一数据源）

所有卡片、图表、节点事实**只读这一份**。此前出现的矛盾（结论说"适合出发"而节点显示"无显著天相"）根源就是多处各自算一遍。

```
TRACK          { name, day, kmTotal, climb, obsAlt, startH, arriveH,
                 sunrise, sunset, moon, stayEndH, staySampleMin }
TRACK_NODES[]  { h, alt, km, ph? }        // 12 点，ph 缺省即"无显著天相"
DAY_FAIR / DAY_OVERCAST                   // 逐日基准数据集
HOURLY[day][hour]                          // 7×24 采样
```

派生（纯函数，不缓存、不落 data）：

| 函数 | 职责 | 关键约束 |
|---|---|---|
| `sample(day, h, field)` | 线性插值取样 | `h ≥ 23` 必须夹到 23 时 |
| `snap(day, h)` | 一次取全字段 | 避免循环里重复插值 |
| `nodeFacts()` | 逐节点天相 + 理由 | 理由必须是**概率语气** |
| `runsOf()` | 连续同天相段 | 主窗口优先取多节点段 |
| `judge()` | 适宜度评分 0–100 + 理由链 | 分数从到达时刻实况推导，不写死 |
| `trackPoints(overnight)` | 生成时空图折线 | `overnight` 决定是否延伸至 23:00 |
| `posAt(pts, t)` | 插值取某时刻的 km/alt | 漫游拖动用 |
| `phenColorAt(phase)` | 天相 → 颜色 | **必须走 token，不得写字面量** |

**线路基准值**（原型实测，正式取值需与 GPX 导入结果对齐）：
`格聂冰川环线 · 52.8km · 累计爬升 2416m · 12 节点 · 05:40 出发 · 14:10 抵达 · 观景位 3900m`

## 4. 视觉与组件设计

### 4.1 时空天相图

五层，自下而上：

1. **地形填充** — 路线下方海拔剖面，弱对比。
2. **云层带** — 云底 ~ 云顶区间，夜间加深。
3. **轨迹带** — 按天相着色的渐变折线，节点为圆点。
4. **标注层** — 主窗口括号、观景位参考线、到达时刻竖线与净空标注。
5. **播放头** — 当前时刻游标 + 行走小人。

关键标注：

- **主窗口括号**：标注起止时间与命中节点数，如「云海 07:55–11:15」。
- **观景位参考线**：`3900m` 横向虚线，标签靠**左**以避让右侧到达标签。
- **到达净空**：轨迹与云顶之间的高差直接标出——这就是"云在脚下"的量，例「净高 1,442m」。
- **无数据区**：抵达时刻之后留白，不做插值假装有数据。

### 4.2 漫游（Scrubber）

拖动滑块或点播放，联动输出：`当前时刻 · 里程 · 海拔 · 天相`。

- 播放头位置由 `posAt()` 插值，**不新建数据源**。
- 到达时刻之后停住，不循环。
- 暗色跟随系统（`usePrefersDark`），**不得条件调用 Hook**——曾因在条件分支里调用导致 `Rendered fewer hooks than expected`。

### 4.3 天象卡（AstroCard）

留宿模式专属。展示**实测窗口**而非泛泛描述：

- 晚霞 `20:10–21:10`
- 银河 `22:10–22:55`

窗口由天文时刻与整点相交判定（沿用 meteogram 的既有做法，窄窗口不能按整点高度角标记）。

### 4.4 文案语气（**硬约束**）

天气派生结论一律概率语气：

- ✅ 「云量抬升，**有**出现云海**的可能**」
- ✅ 「出现云海的**概率较大**，建议 07:55 前进入窗口」
- ❌ 「会有云海」

## 5. 设计系统落地（**复用优先，禁止发明新色值**）

### 5.1 可直接复用

| 用途 | 取值 | 来源 |
|---|---|---|
| 云海主色 | `#346583` | `--info` |
| 显著天相 | `#2D533F` | `--forest` 系（`--leaf-on-forest` 底色） |
| 银河 | `#163E35` | `--forest` |
| 无显著天相 | `#8C9791` | `--control-line` |
| 地形/参考线 | `--line` / `--forest` | token |
| 播放头、强调文字 | `--forest` | token |

渐变端点因此可**完全由既有色构成**：`#8C9791 → #346583`（灰→蓝），无需新色。

### 5.2 必须新增的 token（**本轮主要设计系统债**）

`meteogram.js` 顶部维护着一份 canvas 字面量色板，其中天相窗口色**从未提升为 `app.wxss` token**：

| 色值 | 用途 | 现状 |
|---|---|---|
| `#D6A33C` | 黄金 / 晚霞 | 仅存在于 canvas 字面量 |
| `#6C7C93` | 蓝调时刻 | 仅存在于 canvas 字面量 |

**处理**：本轮在 `app.wxss` 新增这两个语义 token，**同步登记进 `design-system.md` 的 token 表**，并把 `meteogram.js` 字面量改为引用同一份来源。canvas 拿不到 `var()`，所以 JS 侧仍需字面量，但**必须单一来源**并加注释互相指向。

### 5.3 布局约束

- canvas `type="2d"` 在 `node.width` 赋值瞬间锁定图层偏移，**不随后续回流**。异步布局稳定后需重新测量（沿用 meteogram 在 100ms / 320ms 两点测量的做法）。
- 绘制按 `pixelRatio` 缩放，否则文字发虚。
- 新组件**必须**声明 `options: { styleIsolation: 'apply-shared' }`，且 `options` 只能出现一次。
- `page` 级变量挂 `page` 选择器，WXSS 无 `:root`、无 `color-mix()`、无可靠 `dvh`。

## 6. 小程序架构映射

| 原型概念 | 落地位置 | 说明 |
|---|---|---|
| 统一数据层 | `utils/weather-model.js`（新） | **只做轨迹/节点/评分编排，天相判定一律调用 `sky.js`** |
| 时空图几何 | `components/space-time/layout.js`（新） | 对应 `meteogram/layout.js` 的做法：几何抽成模块供测试断言 |
| 时空图渲染 | `components/space-time/`（新组件） | canvas 自绘 |
| 漫游 | `components/roam-scrubber/`（新组件） | 原生 slider + 联动 |
| 天象卡 | 天气页内新增区块 | 复用 `.card` / `.badge` / `.sky-card` |
| 数据获取 | 沿用 `utils/api.js` | 不新增云函数 action |

### 6.1 `weather-model.js` 的边界：**编排，不是重写**

`utils/sky.js` 已经是一个 433 行、wx-free、覆盖 6 种天相的概率引擎，`sky.js` 开头即写明「这是『概率判断』，不是预报产品」。

**`weather-model.js` 不得包含任何天相阈值判定。** 它只负责原型里 `sky.js` 尚未覆盖的那一层：

| 原型函数 | 归属 | 说明 |
|---|---|---|
| `sample` / `snap` | **weather-model** | 逐时插值 |
| `nodeFacts()` | **weather-model** | 编排：对每个节点调 `sky.js` 取天相，**不自己判** |
| `runsOf()` | **weather-model** | 编排：把 `nodeFacts` 的结果切连续段 |
| `judge()` | **weather-model** | 编排：把 `sky.js` 的分数与证据汇成适宜度 |
| `trackPoints()` / `posAt()` | **weather-model** | 轨迹几何 |
| `phenColorAt()` | **weather-model** | **必须查 `meteogram/layout.js` 的 `MARK_STYLE`**，不得自建映射 |
| 天相阈值、文案、窗口 | **`sky.js`（已存在）** | 不动 |

> **两处各算一遍是本仓库最贵的教训。** 原型是独立 React 工程、没有 `sky.js`，所以自带一套判定；移植时若照搬，就会在小程序里出现第二套天相引擎，图表与结论卡可能对同一时刻给出不同结论，且 `sky-test.js` 的 65 例完全测不到新那一套。

### 6.2 mark key 与色板单一来源

`utils/AGENTS.md` 有一条硬契约：

> `sky.js` 的 mark keys 必须与 `components/meteogram/layout.js` 的 `MARK_STYLE` 保持同步。

因此：

- `space-time/layout.js` 的天相色**直接复用 `meteogram/layout.js` 的 `MARK_STYLE`**，不复制一份映射。
- 期 1 提升 token 时，`MARK_STYLE` 是唯一色值来源；`meteogram.js` 的 canvas 字面量与 `space-time.js` 的 canvas 字面量都从它派生，并在两处加注释互相指向。
- 天相 key 若有增删，**必须同批改 `sky.js` + `meteogram/layout.js` + `space-time/layout.js` 三处**，否则图表会静默丢标记。

### 6.3 时间

时间是北京时间、硬编码 UTC+8、无时区库、无 DST（`utils/AGENTS.md`）。原型的 `hhmm()` **不得另起一套**——格式化一律走 `format.js`，不要开第二个日期库。

### 6.4 铁律

- `utils/weather-model.js` **必须 wx-free**，否则会被移出 Node 测试覆盖（`api.js`/`draft.js` 是仅有的两个例外）。CommonJS `module.exports`，无 ESM、无 barrel、无子目录。
- 每个函数必须进 `module.exports`（曾因漏导出导致 27 处调用全为 `undefined`）。
- 跨文件 API 面**用脚本核对，不靠肉眼**。
- 测试**不得复刻页面逻辑**，否则会为过期契约背书——这正是 `meteogram/layout.js` 存在的原因。
- 新 util 必须配测试：**没有测试的 util 是未测试的 util**。
- `weather-page-test.js` 现有 129 例是云函数→页面→组件契约，**改动前先跑基线**（已跑，全绿）。

### 10.1 计划与落地的差异

| 项 | 计划 | 实际 | 原因 |

### 10.7 期 6：留宿 + 夜间天象（已完成，真机核对）

`space-time` 加留宿开关，打开后时间轴延到 23:00 并出「留宿夜间」卡（晚霞 / 银河）。

**复用手法**：`nightOutlook()` 把 `detail` 裁成 `fromH`（默认 18:00）**之后**再交给
`sky.summarize` —— `alpenglowConclusion` 内部的 `isDawn` 判定（`hourMin < 12*60`）必然为假，
它自然返回**昏光**那条结论。阈值、文案、概率语气、证据链全部原样沿用 `sky.js`，
**本轮未新增任何天文判断**。银河是星空子集，两者都成立时只报一个。

**真机核对：** 日落 20:12 · 天文暮光 21:34；晚霞 19:00–20:00 条件较好；银河「22:00 前后」条件一般。

**真机抓到的行为 bug：** `layout.build` 曾用播放头位置撑大 `tMax`（留宿未实现时的权宜之计），
代价是播放头停在 21:30 后关掉留宿，时间轴收不回 14:10（实测 `roamMax=1290` 而非 850）。
现在轴只由数据决定（路线终点或 `stayEndH`），播放头越界一律夹住。
`routeEnd` 改取最后一个**节点**的时刻而非最后一个点 —— 留宿时点被延伸到 23:00，
但路线 14:10 就到头了，拿点当终点会把「已抵达、仍在山里」误判成没走完。

留宿开关是**组件内状态**：只传 `stayEndH` 而不开关**不会**延伸 —— 留宿是产品决策，
宿主误传 `stayEndH` 不该悄悄把轴拉到 23:00。
