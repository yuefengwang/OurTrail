# 10 · Identity Code Design（「协作身份码」的正名与处置）

> 任务书 §17 要求：不能只说「改个名」，必须先弄清它是什么。本文逐问作答，
> 每问先给代码事实。

---

## 1. 它是什么

【CODE FACT】「协作身份码」= `profile.id` = **微信 openid**。
- 生成者：微信平台（用户首次打开小程序访问云函数时由 `cloud.getWXContext().OPENID` 注入，
  index.js:263）——**OurTrail 不生成、不存储第二套标识**；
- 落库时机：首次 `profile.save` 时作为 Profile 主键（profile.js:44）；空壳档案不落库
  （selectors.js:254-256）；
- 展示：me 页 `identity: profile.id` 原文展示 + 复制（me.js:127, 347-352; me.wxml:107-118）；
- 唯一业务用途：**membership.save 的目标账号定位**——组织者把对方身份码贴进协作授权表单，
  服务端按 `state.profiles.some(p => p.id === membership.userId)` 找人（profile.js:19）；
  roster-panel 的输入框 placeholder「粘贴身份码」（roster-panel.wxml:157-159）。

【CODE FACT】它**不等同于**「用户 ID」的完整语义——它就是微信给的账号主键，OurTrail 全域
（isOwner/staffCan/signups.personRef/memberships.userId/头像路径）都用它，协作授权只是
**唯一一个需要用户主动出示它**的场景。

## 2. 逐问作答

| 问 | 答 |
|---|---|
| 谁生成？ | 微信平台（openid），OurTrail 原样采用 |
| 是否唯一？ | 是（每用户每小程序唯一；invariants 要求 Profile.id 全局唯一，invariants.js:13-14） |
| 是否永久？ | 是。openid 不可变更；且不可轮换——`memberships.userId`、`signups.personRef.userId`、`routes.ownerId`、头像云路径全部引用它，轮换 = 全库引用重写 |
| 是否可枚举？ | 不可（openid 是高熵串，无按序/短格式特征）；唯一探测面是 SF-1 的存在性预言机（owner 专属，07 §4，接受） |
| 是否敏感？ | 低。单独持有它做不了任何事：所有读都以「自己的 openid」为轴（服务端从上下文注入，不从参数取），唯一写入口 membership.save 是 owner 专属。它是**可公开出示的账号句柄**，类似「加好友的号码」而非「密码」 |
| 是否用于 membership.save？ | 是，且是唯一用途（profile.js:19） |
| 是否用于查找用户？ | 仅上条；无任何「按码加人/查资料」的 API |
| 是否应显示在首页？ | 收敛——从平铺全文改为缩略 + 复制（见 §4），不出现在 home/其他页 |
| 是否独立「我的同行码」页？ | P0 不建页（03 §2 F 区卡内完成缩略+复制）；P2 若加二维码再评估独立页 |
| 是否需要二维码？ | P2 评估（见 §5）——线下「出示-扫码-授权」比「复制-微信发送-粘贴」少两次跨 App 跳转，但要付出 canvas 生成与 roster-panel 扫码两端改造 |

## 3. 命名裁决

【DESIGN DECISION】**功能保留原样；展示名从「协作身份码」改为「我的协作码」，禁止使用「同行码」。**

【RATIONALE】
- 「协作身份码」的「身份码」过重（暗示身份体系），而它的全部产品语义就是「把协作授权发给谁」；
- **「同行码」与「常用同行人」撞车**：companion 域已经占住「同行」一词（报名勾选对象），
  把 openid 也叫同行码会让两个零关系概念共用一个词头——08 §1 刚刚花整节划清的语义边界
  会被命名亲手拆掉；
- 「我的协作码 + 说明句『组织者把它填进「协作授权」，你才能看到对应任务。』」自解释闭环最小。
  （若产品负责人坚持「同行码」，需同步接受与 companion 的词汇冲突——本文标记为待拍板项，
  不阻塞实现。）

【IMPACT】纯文案（me.wxml F 区 + roster-panel 提示语同步）；identity 变量名不改。

## 4. P0 表达规格（F 区）

```
身份与协作
┌──────────────────────────────────────────┐
│ 我的协作码   oX28a*****(缩略)      [复制]  │
│ 组织者把它填进「协作授权」，你才能看到对应任务。│
└──────────────────────────────────────────┘
```

- 缩略规则：保留前 4 字符 + `…` + 后 4 字符（openid 长度 28±，缩略足以确认非空且非他人码；
  完整值只通过「复制」出口离场）；
- 保留 `user-select` 与复制按钮（线下流转是它的唯一用途，复制是主路径）；
- **激活门**：从未 profile.save 过的用户，其身份码「能用但无用」（组织者贴了必报
  NOT_FOUND，profile.js:19）——F 区在未激活态显示副文案「完善资料后，组织者即可凭码授权你」，
  与 04 的激活引导呼应。

【RATIONALE】缩略解决的是「截图/演示场景下全量 openid 长串裸奔」（03 §1 问题 5），
不改变「主动复制」的产品路径。低收益不动更多。

## 5. P2 展望：二维码（不立项，只记录边界）

- 出示端：canvas 画 openid 文本二维码（纯前端可行，基础库 canvas 能力足够）；
- 接收端：roster-panel 加「扫码填入」（`wx.scanCode` → 校验非空 → 填 mUserId）；
- 收益：线下授权路径从「两台手机四个 App 间跳转」缩为「一扫一确认」；
- 成本：两端 UI + 测试 + 二维码容错（扫错人码的错误提示）；roster-panel 的授权表单同时是
  交互审查 P1#6（撤销无确认）与 P1#7（弹层键盘）的修整区，**宜与那批一起做**，不单独立项。
- 风险提示（记录）：扫码引入「扫错码授错人」的新错误面，需在确认步骤显示解析出的码前缀
  供人工核对。

## 6. 明确不做

- **不自建随机协作码**（如 `OT-XXXX-XXXX` 映射表）：需要新集合/字段 + 查询索引 + 与 openid 的
  双向维护，收益仅是「码更好看」——V1 不值当（任务书 §27）。若 V2 认证体系（certified_leader 等）
  出现「跨小程序/多端身份」需求，再在那时立 ADR；
- 不做「按手机号找人」「通讯录匹配」等替代查找通道（熟人线下传码已闭环，且手机号匹配
  引入新的隐私面）；
- 不做码的「重置/轮换」入口（见 §2 永久性，技术不可行）。
