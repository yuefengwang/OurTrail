# 04 · Onboarding（首次进入与资料激活）

> 目标：新用户感觉「花几十秒完善同行资料」，而不是「被要求授权 4 次」。
> 技术上的多个 API 与产品上的一个流程分离（P7 原则）。

---

## 1. 平台事实底座（2026-10 官方核查，设计以此为准）

【CODE FACT】本项目的身份注入方式：**客户端不需要 wx.login**。云函数从
`cloud.getWXContext().OPENID` 直接获得调用者身份（index.js:263），全链路没有 code2Session 调用。
「已经是 OurTrail 的一个用户」在技术上从打开小程序第一刻就成立——只是**还没有资料**。

【CODE FACT】四个字段的技术形态与授权成本完全不同：

| 字段 | 机制 | 用户感知成本 | 门槛/计费 |
|---|---|---|---|
| 头像 | `button open-type="chooseAvatar"`（填写能力） | 点一下，选「用微信头像」 | 无弹窗、无费用；基础库 ≥2.21.2（本项目 3.8.12） |
| 昵称 | `input type="nickname"`（填写能力） | 键盘上方出现微信昵称快捷条 | 无弹窗、无费用 |
| 手机号 | `open-type="getPhoneNumber"` | **微信弹出授权半屏，用户点允许** | 需认证主体开通权限 + 后台《用户隐私保护指引》声明「手机号」；0.03 元/次成功调用；个人主体未开通时只能手填（本仓已按此降级设计，me.js:275-276） |
| 紧急联系人/健康备注 | 普通输入 | 纯手填 | 无平台成本 |

【CODE FACT】`wx.getUserProfile` 返回匿名数据，本仓 UI 规范明令禁用（ourtrail-ui SKILL.md）——
**设计不得回退到旧 API**。
【CODE FACT】隐私框架：只有后台《用户隐私保护指引》声明了「手机号」，getPhoneNumber 才可用；
未声明时本仓已有指路文案（me.js:273-274）。头像/昵称不属于需声明的隐私接口。

## 2. 设计立场

【DESIGN DECISION】Onboarding 不是一次性弹窗索取全部信息，而是**三段渐进式激活**：

```
段 0 · 隐式身份（0 秒，用户无感）
   打开即有账号（openid），身份码已可用——只是资料为空。
段 1 · 资料激活（30–60 秒，一次性，可跳过）
   头像 + 昵称 + 手机号（可选微信快捷）→ 首次 profile.save = 「激活」。
段 2 · 安全资料（随场景补齐，不进激活流）
   紧急联系人 / 健康备注：引导里给「稍后在『我的』补全」出口；
   真正的强制点在报名表单（signup.normalizedPerson 要求 emergency 姓名电话，signup.js:25-27）。
```

【RATIONALE】
- 段 0 让「我已经是用户」成立：协作码流程（把码给组织者）在激活后即可用；
- 段 1 只含「头像昵称手机号」：这三者构成报名预填与身份显示的最小集，且都是低敏感字段；
  手机号放在激活流里但**可跳过**——跳过者手填（报名表单仍有 number 校验兜底）；
- 段 2 不进激活流的理由：紧急联系/medical 是报名时被服务端强制的字段（signup.js:25-27），
  与其在冷启动时逼用户编，不如让「报名」这个真实场景逼出它——而 Profile 版本作为预填默认值
  （fillFromProfile 只补空字段，signup.js:158-164），第一次报名填过的内容会自动回流档案
  （signup.js:301-321 回写链）。**报名即 onboarding 的第二段**。

## 3. 触发点矩阵（何时出现激活引导）

【CODE FACT】现状四处已经存在「无档案拦截」，但形态各异：

| 场景 | 现状 | Target |
|---|---|---|
| 「我的」Tab 首访（空壳档案） | 直接显示空表单页 | A 组头卡下方出现「完善同行资料」引导卡（非模态），点击进激活 sheet |
| 报名页（profile.person.name 为空，signup.js:79-82） | 拦截 + 文案，无直达 | 拦截卡内嵌「30 秒完善资料」主按钮 → 页内激活 sheet（P1）；P0 先加 `wx.switchTab` 直达按钮（与 editor 的 profileGate 同型，editor.wxml:439 是现成范式） |
| 编辑器保存/发布前（editor.js:559-570） | profileGate + 直达按钮（已修，交互审查止血批 ④） | 不动 |
| 组织者贴身份码但对方未激活（profile.js:19 NOT_FOUND） | 服务端报错文案已含指引（「请对方在『我的』页复制身份码给你」——隐含「对方得先存过资料」） | roster-panel 报错文案追加「（对方需先在『我的』完善资料才会生成档案）」（P1 文案微调） |

【DESIGN DECISION】**引导卡不是模态**：空档案的「我的」页仍是完整 Hub（各区块显示空态文案），
引导卡只是第一个区块。拒绝补资料的用户一切功能可浏览，真正被服务端闸住时再被场景拦
（报名/发布/授权），拦截处都有可操作出口。

## 4. 激活 sheet 的交互规格（段 1）

```
<overlay kind="sheet" title="完善同行资料">
  ① 头像行：圆形头像按钮（chooseAvatar）+ 副文案「点一下，用微信头像」；未选时显示首字回退
  ② 昵称行：type=nickname input（大字无下划线），键盘快捷条出现即一键填入
  ③ 手机号行：number input（手填为主）+「使用微信手机号」文字按钮（getPhoneNumber；
     取消→回落手填并提示一句，不算错误；未开通权限→按既有降级文案）
  ④ 主按钮「完成，开始用 OurTrail」：
     name+phone 齐 → dispatch profile.save（把 sheet 内 emergency/medical 空值一并带上——
     schema 允许空串）→ 成功 toast「资料已保存」→ 关 sheet → Hub 刷新（统计/协作码激活）
     缺任一 → 按钮可用但点击时点名缺项（沿用 persistPerson 的 fieldErrors 语义）
  ⑤ 次级出口「先跳过」：关 sheet 不保存；引导卡保留在页上
</overlay>
```

【DESIGN DECISION】激活 sheet 与「我的」页 D 组编辑 sheet **复用同一套 handler**
（onField/persistPerson 差异仅在成功后的文案与关闭动作），不写第二套保存逻辑。
【RATIONALE】两套保存路径是草稿/revision/CAS bug 的温床（P10 不重写清单）。

【IMPACT】me.js 新增 onboarding 状态（`onboardingOpen`、`activated = !!(person.name && person.phone)`）；
激活完成前 A 组身份行显示「同行资料待完善」态。
【PRIORITY】P0。

## 5. 微信授权在流程中的位置（明确回答「为什么手机号独立授权」）

【DESIGN DECISION】
- 头像/昵称：**产品里不出现「授权」二字**。用户动作是「点头像用微信头像」「昵称一键填入」，
  因为平台本来就不弹窗——把它说成授权反而制造心理成本。
- 手机号：**保留一次明确的用户主动授权**，但授权动作发生在「手机号」这个资料的编辑语境里
  （D 组摘要行/激活 sheet 内的「使用微信手机号」按钮），微信原生半屏弹窗本身就是最好的
  「我在授权什么」说明，页面不再叠自定义确认。取消授权 = 回到手填，永不报错。
- 一切天气/安全结论类文案保持概率语言；资料用途文案统一「用于活动联络与安全应急联系」
  （me.wxml:47 现有句保留为标准句）。

【RATIONALE】任务书 §8 的倾向（「不要让用户看到微信 API」）与平台现实的最小冲突解：
头像昵称本来就无弹窗，收掉文案即可；手机号的弹窗是平台强制的、有法律意义的同意动作，
隐藏它既做不到也不应该。

## 6. 拒绝与降级路径全表

| 用户行为 | 系统反应 | 依据 |
|---|---|---|
| 激活 sheet 点「先跳过」 | 关闭，Hub 空态引导卡保留；功能浏览不受限 | 本设计 |
| 手机号授权弹窗点取消 | hint「已取消获取微信手机号，可手动填写。」（现状保留） | me.js:268-271 |
| 手机号权限未开通（1400001） | 降级文案「请手动填写」（现状保留） | me.js:275-276; index.js:211-214 |
| 隐私指引未声明手机号 | 指路后台配置的详细文案（现状保留） | me.js:273-274 |
| 头像上传失败 | 「头像上传失败，请重试。」（现状保留） | me.js:249 |
| 只填紧急联系人/medical 就离开 | 草稿接管（本机留存 + 待保存横幅），激活后自动一起落库 | me.js:164-181 现状机制 |

## 7. 不做清单

- 不做启动页/引导轮播/角色选择（多角色权限模型 §7.1：默认参与者视角，无启动角色页）；
- 不做「微信一键同步全部资料」聚合按钮（getPhoneNumber 是唯一有授权语义的字段，
  头像昵称本就零成本；聚合按钮会制造「授权了什么」的误解）;
- 不做强制激活墙（浏览/发现页零拦截，discover 的 denied 仅在未登录时出现，selectors.js:293）；
- 不在 P0 引入 wx.requirePrivacyAuthorize 自定义隐私弹层（privacy-popup 已确证死代码并保留；
  平台对已声明指引的小程序使用默认隐私弹窗即可，自定义化列为 P2 观察项）。
