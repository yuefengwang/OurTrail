# OurTrail 竞品设计研究 V1

研究日期：2026-10-26。交付范围：公开界面研究、交互规则核对、OurTrail 设计方向与组件借鉴建议。配套 [视觉参考板](index.html) 可离线打开，点击图片可查看原图。

## 结论：用 Luma 组织活动，用 AllTrails 表达路线，用 komoot 和 Windy 处理专业信息

建议把 OurTrail 定位成「清晰、亲近、可靠的同行工具」。以 **Luma 的日期组织、名单结构与操作层级**作为主要结构参考，以 **AllTrails 的路线指标层级**补足户外表达；地图节点参考 komoot，天气图表参考 Windy。Partiful 只借邀请页的亲近感，两步路只借中文户外术语和路线信息组织。

这不是把六款应用拼成六种皮肤。全局统一文字、间距、控件与状态；活动介绍、组织者名单、现场执行、天气图表采用不同的信息密度。真正应推翻的是所有页面都用同一种大卡片、同一种装饰性头图、同一种仪表盘的做法。此前原型中的橙色或现有小程序的绿色，均不作为这次方向选择的前提。

## 研究方法与证据边界

- 选择依据：覆盖「理解活动 → 报名 → 组织名单 → 出行与现场执行 → 查看天气」这条任务链，而非只找视觉相似的户外应用。Luma、Partiful 是活动组织参照；AllTrails、komoot、两步路是户外参照；Windy 是专业信息参照。
- **视觉证据**：逐张查看官方站点图和开发者上传的 App Store 宣传截图。图片含营销包装，不能据此确认安装版每个细节、字体、精确色值或交互性能。
- **功能证据**：官方帮助文档核对名单筛选、报名审核、地图节点、天气来源等。管理页没有直接界面证据的地方，明确只采用文档证据。
- **代码证据**：核对 OurTrail 页面注册、服务端数据投影、状态翻译层。这里的建议不构成新增能力已实现的声明。
- **未执行**：登录竞品账号、创建真实活动、付费、端到端可用性测试、实地阳光可读性测试。不以 App Store 宣传语或排名作为体验优劣的证明。
- 所有来源于 2026-10-26 访问；该日期不是截图版本发布日期。精确图片 URL 见 [sources.json](sources.json) 与 [store-assets.json](store-assets.json)。图片权利归原权利人，仅作内部研究参考，不作为 OurTrail 可发布素材。

## 01 · Luma：最适合借鉴的活动组织骨架

**观察到的风格。** 官方截图中，日历页用白底、黑色标题、细灰辅助信息，日期作为纵向分组；活动行配小缩略图。活动详情则允许独立主题和大海报，标题、主办人、时间、报名操作构成清晰的阅读顺序。它把内容页的表现力和日常列表的效率分开。见 [官方 App Store 图](https://apps.apple.com/us/app/luma-events-invites/id1546150895)，本地参考 `luma-3.webp`、`luma-4.webp`。

**文档确认的机制。** 名单按状态筛选并显示数量，搜索与当前筛选同时生效；待审核、候补标签按实际情况出现。打开人员详情可查看报名答案并处理。审核与签到分开。此处是帮助文档证据，未操作实际管理界面。[名单管理](https://help.luma.com/p/managing-your-guest-list)

**OurTrail 借鉴。** 首页按近期日期组织活动，活动行说明「我参与 / 我发起」和下一步；工作台顶部显示待处理数量，下面直接进入人员列表。人员行只露出姓名、报名状态、出行方式和当前必要操作，敏感信息在授权后的详情展示。现场签到另设清楚的任务范围，不能把「已通过」当成「已到场」。

**必须改造。** Luma 的 Web 批量工具在选中行后出现，并区分选中集合与全体动作。OurTrail 可借其明确作用范围的原则，但手机应使用选择态底部工具栏；新增批量行为须先核对已有命令和逐人失败反馈，不能把桌面表格缩小塞进手机。[扩展名单表](https://help.luma.com/p/expanded-guest-table)

**不借。** 票务、支付、内置聊天、公共社群增长；微信群已承担交流，OurTrail 重点是共同名单和履约。也不直接移植 iOS 导航结构。

## 02 · AllTrails：让户外内容先可判断，再可浏览

**观察到的风格。** 探索页白底、大片自然摄影、横向条件筛选；路线卡把名称与地点分层，再把难度、距离、耗时紧凑排列。详情页从照片进入白色内容区，距离、爬升、预计时间和路线形态独立成组；主要操作使用高明度绿色，次操作减弱。图像吸引注意，指标帮助决定。见 [官方 App Store 图](https://apps.apple.com/us/app/alltrails-hike-bike-run/id405075943)，`alltrails-2.webp`、`alltrails-3.webp`。

**功能核对。** 官方把前往起点的 Directions 与沿路线活动的 Navigate 区分，这种对象区分值得借鉴。[入门说明](https://support.alltrails.com/hc/en-us/articles/37200401098516-Getting-started-on-AllTrails)

**OurTrail 借鉴。** 活动详情首屏回答活动名、日期、集合地点、距离/爬升、报名状态；路线指标固定顺序，数字和单位分层。集合点的位置入口与路线节点入口分开命名。长装备说明与风险说明放在后续章节，关键风险摘要仍须可见。

**必须改造。** OurTrail 活动投影没有稳定封面字段；发现列表甚至没有轨迹线投影。默认采用日期块与文字列表。有真实轨迹的详情才可展示轨迹缩略图；无轨迹时不生成假路线。若以后引入摄影封面，需要补数据、上传、授权及内容审核链路，不能先铺样片假装可落地。

**不借。** 评分、推荐榜、下载离线地图、跟随导航、路线照片社区；现有能力不能被这些界面暗示替代。也不把每条活动卡都拉成占半屏的大照片。

## 03 · komoot：地图和操作保持在一个上下文

**观察到的风格。** 官方功能图采用浅米色内容区、克制的橄榄色操作、自然摄影和清晰路线线条。规划界面地图占主面积，节点列表和高程剖面与之配合；手机通过底部面板展示当前地点和添加动作。筛选控件依据任务采用复选项、范围选择、标签，不全部做成相同卡片。[官方功能页](https://www.komoot.com/features/)；本地 `komoot-discover.png`、`komoot-plan.png`。

**功能核对。** 路线规划允许添加和重排途经点；节点编辑应保留前后关系和撤销路径。[路线规划帮助](https://www.komoot.com/help/routeplanner)

**OurTrail 借鉴。** 路线编辑采用「节点顺序 → 当前节点详情 → 地图位置」的统一上下文。地图选点后回到原节点，列表高亮对应对象；查看天气也保留当前节点及海拔来源，避免用户不断重新认位置。GPX 导入后先展示可识别节点、路线指标及缺失信息，再进入编辑。

**必须改造。** OurTrail 是活动路线快照与节点工具，不能用画线操作暗示已有自动寻路。只有已有坐标才能定位，没有海拔就标缺失；从 GPX 时间推算的行程不能伪装成实际抵达时间。

**不借。** 自动路网规划、离线导航、语音导航和未经许可的地图素材。地图底图许可和微信原生 map 能力是实施边界。

## 04 · Partiful：邀请页可以有人情味，执行页要有秩序

**观察到的风格。** 官方邀请图用显眼活动名称、方形主题图和个性化背景，时间地点紧随内容；不同活动可使用完全不同的氛围。这适合熟人分享，因为活动本身比工具品牌更值得突出。见 [官方邀请介绍](https://partiful.com/invitations/online-rsvp)，`partiful-invitation.jpg`。图外的气球等是营销构图，不是可直接移植的产品控件。

**功能核对。** RSVP 设置集中处理是否接收报名、审核、人数上限、候补和携伴限制。[RSVP 设置帮助](https://help.partiful.com/en-us/articles/15525368-how-do-i-modify-the-types-of-rsvps-that-are-allowed)

**OurTrail 借鉴。** 分享落地页先让人理解「谁组织、什么时候、去哪、我怎么加入」。创建流程按活动信息、路线集合、报名规则组织，而非按数据库字段顺序堆表单。报名按钮文案反映实际后果：需要审核时，提交后说明等待审核，不能直接显示报名成功。

**必须改造。** 户外活动有紧急联系人、出行方式、装备与风险提示；不能为了轻快把必要信息删掉。携伴报名需保留本人/代填及同意边界。

**不借。** 荧光渐变、全页动效、随活动变化的管理页皮肤；邀请页的情绪价值不应侵入签到和天气。资料不足时不自行简化成一键 RSVP。

## 05 · Windy：专业感来自读数关联和可追溯性

**观察到的风格。** 官方宣传截图里的地图占主空间，深灰面板收纳信息；色彩主要编码气象数值，时间轴、单位和图例与地图并置。飓风示例保留对象、时刻、模型来源与更新时间，帮助解释当前画面。见 [官方 App Store 图](https://apps.apple.com/us/app/windy-com/id1161387262)，`windy-5.webp`。不把风暴场景本身作为 OurTrail 功能需求。

**文档核对。** 地点预报更新强调体感温度、可预测性提示、不同预报展示与数据来源入口。可预测性依赖其模型能力，不能只复制彩色圆点。[地点预报更新](https://www.windy.com/articles/43908)

**OurTrail 借鉴。** 天气页采用「地点/节点与日期 → 简要条件 → 同轴图表 → 证据解释」。选择时刻后，温度、风、降水、云层读数应对应同一时刻；图例和海拔单位就近显示，来源和更新时间可找到。主色退出图表编码，避免把品牌绿误当作低风险。

**必须改造。** OurTrail 天相已有 possible/excluded/unknown 语义；缺数据应解释缺什么，不能显示为零。客观日出日落时刻与拍摄机会分开。显示窗口、业务扫描范围和有数据范围必须分别表达。未来设计应保留现有科学语义，不能用新的漂亮总分抹掉边界。

**不借。** 未接入的多模型比较、雷达、实时警报、概率和置信度。也不据深色宣传截图就认定全站深色更适合户外；日间可读性需另行验证。

## 06 · 两步路：吸收中文户外表达，控制工具密度

**观察到的风格。** 官方商店截图显示白底与绿色强调色；路线页使用缩略图加紧凑指标，里程、爬升、耗时易于横向比较。地图页以高对比轨迹、起终点标识、侧边工具和底部面板组织操作。见 [中国区官方商店页](https://apps.apple.com/cn/app/id646277024)，`2bulu-2.webp`、`2bulu-3.webp`。

**OurTrail 借鉴。** 路线指标用熟悉的「里程 / 爬升 / 耗时」语言，起终点同时以文字与形状区分；节点列表与地图关联。现场模式缩短操作路径，关键动作有文字而非纯图标。

**必须改造。** OurTrail 以一次活动和同一份人员名单为中心，默认页面只呈现当前阶段所需工具。两步路截图中的大量侧边工具不能原封不动复制；自驾、自行前往和拼车状态要据 OurTrail 语义设计。

**不借。** 双列内容瀑布流、商城、赛事推广和同时展开的工具矩阵。商店素材只证明其公开展示风格，不证明操作效率或全部功能现状。

## 横向归纳：把借鉴落实到任务，而非品牌拼贴

| OurTrail 任务 | 主要参考 | 应采用的设计规则 | 需要防止的问题 |
|---|---|---|---|
| 找到近期同行活动 | Luma 日期列表 | 日期分组、明确个人角色与下一步 | 把首页做成照片推荐流 |
| 决定是否参加 | AllTrails + Partiful | 活动信息先行、路线指标固定排序、一个主行动 | 缺图仍用大面积假封面 |
| 创建活动 | Partiful 设置组织 + komoot 节点上下文 | 分组填写、保留草稿、路线有序编辑 | 引入没有数据支持的新字段或自动规划 |
| 审核与候补 | Luma 名单机制 | 状态数量、筛选内搜索、人员详情承接操作 | 将审核、出行、签到压成一个状态标签 |
| 分车和集合 | Luma 列表原则，OurTrail 自身规则 | 按车分组，单独呈现自行前往 | 把自行前往算作未分配 |
| 签到及收尾 | Luma 签到区分，OurTrail 自身规则 | 任务明确、人员可搜索、操作后有实际结果 | 套用二维码票务或把上车当签到 |
| 路线与节点 | komoot + 两步路 | 地图/列表联动，当前节点上下文连续 | 假导航、假定位、假轨迹 |
| 天气判断 | Windy | 同轴读数、单位图例、来源证据和未知态 | 装饰性评分替代真实条件 |

## 三种可落地风格方向

以下是设计判断，不是竞品优劣评分，也不是从截图采样出来的 token。

| 方向 | 视觉组成 | 最适合 | 代价与适配 |
|---|---|---|---|
| A 清晰的同行工具（推荐） | 白底、深墨文字、深青绿操作、小面积浅底分组；标题和数字建立层级 | 活动、名单、现场操作，兼顾天气 | 不依赖摄影素材；靠真实信息质量建立吸引力 |
| B 山野编辑式 | 暖白、橄榄色、自然摄影、较大标题和章节留白 | 路线详情、邀请内容 | 现阶段缺封面来源；列表和现场页必须收紧密度 |
| C 专业户外仪表 | 中性深色、较紧密读数、地图/图表占主空间 | 天气、地图、夜间查看 | 全站使用偏重；日间对比与高亮状态需要设备测试 |

**推荐 A 作为全局基础，吸收 B 的内容分章、C 的读数严谨性。** 不做三套主题切换，不让每页随意选皮肤。A 与现有绿色在色相上可能接近，但重构幅度来自页面职责、列表形态、动作层级和空间分配，不靠换一个颜色制造变化。

### A 方向的设计参数草案

这些值供下一版设计稿使用，尚未写入生产 token；不是复刻竞品色值。

| 项目 | 建议值 / 规则 |
|---|---|
| 页面底色 / 内容面 | `#F6F7F5` / `#FFFFFF` |
| 主文字 / 次文字 | `#17211D` / `#56635B`；重要信息不使用浅灰 |
| 主操作 | `#245C48` 底 + 白字；每个任务区只有一个最强操作 |
| 分隔线 | `#DCE2DD`；只作分组边界，不承担唯一交互识别 |
| 待处理 / 失败 | `#8A4B12` / `#B42318`；同时带文字和图标，不只换色 |
| 字号层级 | 页标题 24–28，章节 18–20，正文 16，辅助 14；图表标签需按实际尺寸校验 |
| 间距 | 4/8/12/16/24/32；正文左右留白 16–20，密集名单用行分隔 |
| 圆角 | 控件 10–12，内容组 14–16；标签可以胶囊，避免所有容器都胶囊化 |
| 阴影 | 普通列表不加阴影；仅浮层需要清楚的遮挡关系 |
| 触控 | 主按钮约 48 高，图标可视尺寸小但命中区域至少 44×44；原生小程序按实际逻辑像素换算 |
| 图标 | 统一线性图标，按钮配文字；不用 emoji 代替业务状态或工具图标 |

### 六个优先重做的组件

1. **活动行**：日期块 + 活动名 + 地点/路线指标 + 我的状态；不预留空封面。列表可紧凑，详情再展开。
2. **活动概要**：标题、时间集合、路线指标、报名状态，底部主操作绑定角色和阶段。主按钮不能一直叫「报名」。
3. **人员行**：姓名为主；审核状态与出行方式分开；上下文操作可读。长姓名换行，紧急联系人不在列表裸露。
4. **状态筛选栏**：标签加数量、选中态明确；筛选与搜索范围同时可见。空结果允许清除筛选，不能误导成活动无人。
5. **节点详情面板**：点名、位置、海拔来源、关联时刻；地图与面板共享选中项。没有坐标则不给看似可用的定位动作。
6. **天气证据区**：结论、对应时间、条件读数、来源或缺失原因相邻；图表交互选择时刻后更新读数，不新增虚构概率。

## 与真实代码和页面的落点

| 页面 / 组件 | 依据与可用数据 | 设计落点 |
|---|---|---|
| `pages/home`、`pages/discover`、`components/activity-card` | `domain/selectors.js` 的 discoverView；没有封面和轨迹线投影 | 日期/文字活动行；不能借详情能力假设列表也有轨迹 |
| `pages/activity` | activityView 有时间、容量、路线指标、可选 track、集合点、装备与风险 | 信息分章、指标组、与角色相符的底部操作 |
| `pages/editor`、`pages/signup` | 路线快照、集合点、报名规则、身份/紧急联系/出行和同意信息 | 分组表单与上下文编辑；不要删必要字段 |
| `pages/workspace`、`components/roster-panel`、`person-row` | 角色受限名单、permittedActions；occupied = confirmed + pending | 状态筛选、人员处理；候补不混入占位数 |
| `components/transport-panel`、`pages/vehicle` | 出行方式、车辆和去回程状态 | 按车组织，独立显示自行前往，去回程不混淆 |
| `components/field-panel`、`pages/staff` | 现场任务和授权动作 | 任务范围清楚、操作后果明确，签到/登车/到家不合并 |
| `pages/weather`、`weather-chart`、`components/meteogram` | `sky.js`、`cloud-layer-facts.js`、`agenda.js` 的科学语义 | 保留未知态、层范围、时刻与机会边界，优化可读性 |
| 跨页面状态 | `utils/journey.js` 唯一状态与下一步翻译层 | 设计稿文案回到已有状态映射，不自造另一套状态 |

路径以仓库根目录为基准。核心核对入口：[服务端投影](../../../cloudfunctions/trailApi/domain/selectors.js)、[状态翻译](../../../miniprogram/utils/journey.js)、[页面注册](../../../miniprogram/app.json)。分车与现场任务没有在这六款应用中找到足够同构的证据，不硬贴竞品名称当作成熟方案。

## 下一版设计稿的验收题

- 不看说明文字，能否在首页找到最近的活动，并知道自己下一步做什么？
- 无封面、无轨迹、长活动名的真实数据下，页面是否仍成立？
- 组织者能否分清待审核、候补、未分车与自行前往？数量是否仍来自原有业务口径？
- 报名提交后、名单操作失败后、版本冲突后，是否有可理解的状态与恢复动作？
- 现场页面是否明确正在处理签到、去程登车、回程登车或到家确认？
- 天气结论是否能追溯到同一时刻/节点的证据？缺数据有没有被误画成好天气？
- 375/390/414 宽度、长中文和大字号下，关键按钮及图表单位是否可读？

本轮完成研究与风格提案，没有修改小程序生产文件。下一阶段应先用 A 方向制作活动详情、组织者名单、天气详情三个差异最大的页面，再检查同一视觉系统能否承载不同密度；无需先批量换全站颜色。
