# CSS ↔ WXSS 兼容性清单（三分类）

原型是浏览器渲染的 CSS；小程序是 WXSS + WXML。差异不是"差不多就行"，每条都要落到
一个处置：**A 有等价写法**（照做，不登记差异）、**B 写法不同、可能等价**（实测通过才算解决）、
**C 不可等价**（登记为平台差异，升级产品决定）。

> 升类规则：B → A 必须附一次目标侧**实测**（真机读数或截图），静态推断只能让一条停在 B。
> 本清单的 C 类必须同时出现在 `acceptedDifferences[]` 里，并写明"这条差异下仍然比什么"。

## A 有等价写法（不登记为差异）

| 原型写法 | 小程序写法 | 依据 |
|---|---|---|
| `:root { --x: … }` | `page { --x: … }`（WXSS 没有 `:root`） | 平台坑记录；静态可验 |
| 组件内直接用全局变量/全局类 | 组件 `options: { styleIsolation: 'apply-shared' }` | 组件默认样式隔离；漏了会出现"变量能解析、`.card` 没样式" |
| `color-mix(in srgb, …)` | 预算是字面量色值（不许运行时混色） | WXSS 无 `color-mix()` |
| `100dvh` / `100svh` | 固定 `px`/`rpx`，或 JS 量一次高度 | `dvh` 在 WXSS 内不可靠 |
| 遮罩关闭用 `opacity: 0` | `opacity: 0; pointer-events: none; visibility: hidden`（三件套） | 只写 opacity 的遮罩仍吃掉所有点击 |
| `:hover` 表达可点 | `:active` + 显式状态字段 | 触屏没有 hover |
| 一个 `Component()` 里两处 `options` | 合并成一处 | 第二处会静默覆盖第一处，`styleIsolation` 被吞 |
| 子选择器/后代选择器写样式 | 类名直挂（WXSS 支持部分选择器，但组件边界会切断） | 组件边界是硬边界 |

## B 写法不同、需实测确认（未实测前一律 UNVERIFIED）

| 原型写法 | 小程序候选写法 | 要实测什么 |
|---|---|---|
| `::before` / `::after` 画装饰/分隔线 | WXSS 同样支持伪元素 | 捕获快照里伪元素**不是节点**；只有像素能证明它画出来了 |
| `background-image` 内联 `data:image/png;base64,…` | 落成文件再引用 | 本项目实测：地图 marker 拒绝 base64；其他位置需逐个确认 |
| Web 字体 `@font-face` | `wx.loadFontFace` | 首屏字体是否就绪；未就绪时字宽/行高会变，必须重拍 |
| `overflow: auto` 局部滚动区 | `scroll-view` | 自动化滚动只认数字 `pageScrollTo`；元素级滚动在驱动里可能没有通路 |
| `position: sticky` 吸顶 | WXSS 支持，但与页面滚动容器耦合 | 滚动后固定/吸顶元素的坐标基准（见适配器 WX-09，本身未证） |
| 阴影/圆角/渐变 | 直接用 | 逐项比对计算样式 + 像素；渐变在截图上可能被 DPR 缩放糊掉 |

## C 不可等价（登记为平台差异，必须升级）

| 原型元素 | 为什么不可等价 | 报告里必须写 |
|---|---|---|
| 浏览器状态栏 / 地址栏 | 不属于页面，原型外壳与真机外壳不同 | 已把哪个元素设为对齐锚点；`dy` 差是外壳差，不是版式偏差 |
| 微信原生导航栏 / 胶囊 / 状态栏 | 由框架绘制，不在 WXML 节点树里，无法用选择器配对 | 页头只能靠像素或自定义导航；选择器配对在此处 UNVERIFIED |
| 原生 `picker`、相册选择、分享面板 | 系统 UI，自动化驱动不可达 | 交互检查 BLOCKED（不是 FAIL，也不是 PASS） |
| 浏览器 hover / 右键 / 键盘焦点环 | 触屏无对应事件；焦点环由平台决定 | 用状态字段替代；焦点类结论 UNVERIFIED |
| 浏览器 DevTools 的 `getComputedStyle` | 小程序侧没有 DOM/CSSOM（探测见 `docs/research-report.md` §5） | 只能读元素 API 的计算样式；整树样式扫描 UNVERIFIED |

## 使用方式

1. 先按本表把每条差异归到 A/B/C，写进 `platform-mappings.json`。
2. A 类不登记差异，直接把要求写进实现任务。
3. B 类保留在"待实测"清单里；每做一次实测就把日期、设备、读数补上，再决定升 A 还是退 C。
4. C 类必须出现在 `acceptedDifferences[]`：`reason` 说清原因，`categories` 只覆盖真实受影响的维度，
   并在交付说明里写"这条差异下仍然比什么"（例如：不比绝对 `dy`，但比 padding 与字号）。

**禁止**：用"平台差异"当通用挡箭牌接受尺寸/字号/间距偏差；那三类差异在 A/B/C 里都找不到落脚点。
